## 一句话概括

> **我们用三套机制分别根治 LLM 自动出题的三类顽疾：**
> - 用 **Code as Truth** 治事实性错误（让代码算，不让模型脑内算）；
> - 用 **可证伪断言 + 带路由的审核** 治题干漏洞（让"考没考到点"可被机器检出）；
> - 用 **K1–K5 认知雷达 + 知识图谱** 治难度与内容偏离（把"难度""考点"变成客观、可检索的量）。
>
> 在此之上，一条 **确定性原理**（题干自洽 × 建模可行 = 答案确定）贯穿审核，一条 **模型驱动收敛** 哲学贯穿交互。最终目标是**从"会解题"走向"会出题、会诊断、会自适应"**。

# 第一部分 · 诊断：LLM 自动出题的三类顽疾

用 LLM 自动出题，看似简单，实则产出的题目"肉眼看着像题，仔细一查全是病"。我们把顽疾归纳成三类，它们分别指向一个共同的根因：**LLM 出题缺乏"客观真相"和"可机检判据"，靠脑内推理出题 + 审题，错的地方恰是它最自信的地方。**

## 顽疾一：题干漏洞（题目本身逻辑不自洽）

**症状：题目能读懂，但"做不下去"或"答案不唯一"。**

| 子问题 | 举例 |
|--------|------|
| 参数互相矛盾 | 位宽 8 位，却要求表示超出范围的数值 |
| 条件缺失或冗余 | 算法题没说明输入规模；或塞了无关的干扰数据 |
| 隐含前提未声明 | 默认"单链表带头结点"，却没在题干说明 |
| **通过条件无法判定** | **核心病**：AVL 题通过条件只写"树保持平衡"——零次旋转也满足，等于没考旋转辨析 |

> **为什么最致命：** 它不是"答案错"，而是"题目本身立不住"。学生再聪明也答不出一个坏题。这类问题靠人审耗时，靠模型自检往往"自我感觉良好"而放过。

## 顽疾二：事实性错误（内容算错、记错）

**症状：题目没问题，但模型给出的参考答案 / 数值 / 机制是错的。**

| 子问题 | 举例 |
|--------|------|
| 数值算错 | AVL 连续插入的平衡因子推演，第 3 步算错，整棵树后续全错 |
| 公式 / 定理记错 | 把快排的 partition 逻辑套到归并排序上 |
| 机制误判 | 误判页面置换算法的实际淘汰顺序 |
| 推理链过长而断链 | 5 步以上的状态跟踪，模型常在第 4、5 步偏离 |

> **为什么难治：** 一次性"让模型解题并自检"是死循环——用会犯错的模型去检查它自己犯的错，错的地方往往恰是它最"确信"的地方。**靠脑内推理无法根治脑内推理的错误。**

## 顽疾三：难度与内容偏离（出得"像题"，但不是"要的题"）

**症状：题目质量尚可，但跟教师的需求对不上。**

| 子问题 | 举例 |
|--------|------|
| 难度跑偏 | 要一道"标准中等题"，模型给出了一个冷门边界 case |
| 考点偷换 | 本考"页面置换"，结果考成了"进程调度" |
| 风格不符 | 期末卷难度，却被换成了考研级 |
| 整卷重复 | 一张卷子里三道题都在考同一类陷阱 |

> **为什么普遍：** "中等难度""考机制"这类词是主观的、不可复现的。没有可测量的难度定义，就没有"是否达标"的判据。这是整条出题链路最缺乏"地基"的一环。

## 三类顽疾的共同根因

```
题干漏洞 ──┐
事实性错误 ─┼──→ LLM 出题缺乏"客观真相"和"可机检判据"
难度偏离 ──┘      靠脑内推理出题 + 审题，错的地方恰是它最自信的地方
```

**我们的核心思路，就是给这三个根因分别对症下药。** 下面的第二部分逐一展开。

# 第二部分 · 五大核心设计机制

| 治什么顽疾 | 设计机制 | 一句话 |
|-----------|---------|--------|
| 事实性错误 | **机制一 · Code as Truth** | 数值让代码算，模型只写代码、抄结果 |
| 题干漏洞 | **机制二 · 可证伪断言** | 把"考什么"翻译成可机器检出的 assert |
| 难度偏离 | **机制三 · K1–K5 认知雷达** | 把"难度"拆成五维可量化、可检索的量 |
| 考点跑偏 | **机制四 · 知识图谱** | 把大纲变成可检索、可注入的考点结构树 |
| 整体质量 | **机制五 · 带路由的审核循环** | 审核不只判通过/不通过，按问题类型精准回退 |

> 这五大机制之上，还有一条贯穿审核的**确定性原理**和一条贯穿交互的**模型驱动收敛**哲学（见第三、四部分）。

---

## 机制一 · Code as Truth —— 把"算"交给代码（治事实性错误）

> **核心思想：凡涉及数值、状态、结构的内容，一律由可执行代码算出来，LLM 只负责"写代码"和"抄写结果"，绝不"脑内计算"。代码跑出什么，真相就是什么。**

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  题干        │ ──▶ │  求解智能体    │ ──▶ │  可执行代码    │
│ (question)  │     │ 写 gen.py    │     │  gen.py      │
└─────────────┘     └──────────────┘     └──────┬───────┘
                                                │ exec 跑出真实数值
                                                ▼
                                        ┌──────────────┐
                                        │  文档智能体    │
                                        │ 忠实抄写结果   │ ──▶ solution.md
                                        └──────────────┘
```

**关键纪律（三条）：**
1. **代码是唯一真相**。`gen.py` 跑出什么，答案就是什么。
2. **文档智能体只做"忠实抄写"，禁止重新计算**——抄错容易查，算错查不出。
3. **审核智能体对照代码与 exec 输出核查，不在脑内重算。**

**为什么有效：** 把"易幻觉的多步推理"变成"可执行、可断言（assert）、可复现的代码"。数值对不对，跑一遍就知道，不依赖模型对自己的"信心"。

> 真实对照（AVL 树连续插入平衡辨析题）：纯脑内推理时，模型凭空编造不存在的结点"35"、把旋转类型记混（把 LL 说成 RR）；用 Code as Truth 后，机器算出真实形态"根20/右30/30的左右是25和40"，35 这个值在代码里根本不存在——错误被结构性消除。

## 机制二 · 可证伪断言 —— 锁定考点（治题干漏洞）

> **核心思想：题干必须声明"题目成立 ⇔ 某个能被代码检出的客观特征"，并把它翻译成代码里的 assert。不满足就立刻报错。**

```
题干声明通过条件，例如：
  "本题成立，当且仅当：插入序列至少触发 1 次 AVL 旋转"
                    │
                    ▼
          ┌────────────────────┐
          │  题干审核智能体       │
          │  判断通过条件是否：    │
          │  ① 存在              │
          │  ② 可证伪(能检出"没满足")│
          │  ③ 覆盖考察目标       │
          └────────────────────┘
```

**断言必须满足三个性质：**

| 性质 | 含义 | 反例（废断言） |
|------|------|--------------|
| **存在性** | 题干必须声明通过条件，不能"考啥都行" | 通过条件留空 |
| **可证伪性** | 必须能检出"没满足"的情况 | `assert is_balanced(root)`——对任何合法 AVL 插入都成立，检不出"没考旋转" |
| **覆盖性** | 断言要覆盖题目声称的考点 | 声称"考旋转辨析"却只断言"树平衡"，零次旋转也满足 |

**断言的真实威力是拦截坏题：**

> 假设出题智能体手滑，出了一道声称"考 LL 旋转辨析"的题，但参数选成了会触发 3 次 RR 旋转的序列。
> ```python
> assert rotations == [('LL', 30)]   # 题干预期 LL，实际是 3 次 RR
> # AssertionError: 旋转记录不符: [('RR',10),('RR',10),('RR',20)]
> ```
> 断言失败 → 触发回退修复。**断言不是"检查答案对不对"，而是"检查这道题到底考没考到它声称要考的东西"。** 没有它，模型会出大量"看着像题、实际没考到点"的空壳题。

**断言与 Code as Truth 的配合：** 代码提供真相（算得对），断言守住质量（考得对），缺一不可。

## 机制三 · K1–K5 认知雷达 —— 让难度可量化（治难度偏离）

> **核心思想：把"难度"从主观形容词，拆成五个正交的认知维度，每维 1–5 分。难度变得可测量、可对比、可检索。**

难度不是单一标量，而是**一道题消耗考生哪类认知资源、消耗多少**。五个维度各管一种认知需求：

```
                      K1 基础认知需求
                  (需调用概念/术语/公式记忆)
                          5
                         /|\
                          |
   K5 跨域联动需求 ───────┼────── K2 单步代入需求
   (跨子系统传递状态)      │      (执行单次计算/换算)
                          |
                         \|/
                          1
                 K3 机制推演需求  ←  K4 条件路由需求
              (明确规则下多步串行) (识别隐含前提/避开陷阱)
```

**每个维度的 1–5 分标准（节选）：**

| 维度 | 1 分 | 3 分（标准） | 5 分 |
|------|------|-------------|------|
| K1 基础认知 | 仅需常识 | 必须准确记核心概念 | 纯概念辨析，无绕过余地 |
| K2 单步代入 | 几乎不算 | 常规公式代入 | 整题卡这一步复杂计算 |
| K3 机制推演 | 无需推演 | 3–5 步固定流程 | 极长程，错一步全盘输 |
| K4 条件路由 | 题面即全部 | 有明确陷阱词 | 专为反直觉设计 |
| K5 跨域联动 | 单一知识点 | 两系统单向拼接 | 多系统深度耦合双向推演 |

**难度怎么从真题里"抽取"出来（三步链路）：**

```
第①步 单题打分：题库真题(2000+) 每道按五维 1–5 分标注
        │       → 每题一个 K 雷达指纹 {K1:4,K2:2,K3:4,K4:3,K5:1}
        ▼
第②步 题位聚合：按题位(如选择题Q12)统计多年真题
        │       → 题位难度锚点：每维 众数(mode) + 范围(range)
        ▼       → 回答"这个题位通常多难、允许多难"
第③步 K 值检索：出题时按目标 K 雷达做 MAE 排序
                → 找认知负荷最接近的往年题作参考
                → 出题锚定往年同类题，不凭空生成
```

**两个关键设计决策：**

1. **为什么用"众数 + 范围"做锚点？** 众数回答"这个题位*通常*多难"，范围回答"*允许*多难"。出题时目标 K 值必须落在锚点范围内，否则就是难度偏离。

2. **为什么用 MAE（平均绝对误差）检索，而不是比"难度总分"？** 因为两道总分相同的题，难度形状可能完全不同——一道是"计算难"（K2 高），一道是"推演长"（K3 高）。MAE 比的是**五个维度的逐维差距**，能找到"不仅难度相当、连难度类型都相似"的参考题。这是更精确的难度匹配。

**难度锚点最终进入设计卡**（见第三部分），成为整道题的"难度宪法"，下游不得修改。

## 机制四 · 知识图谱 —— 考点的"地图"（治考点跑偏）

> **核心思想：把 408 大纲变成一棵可检索、可注入的考点结构树，让系统知道每个考点在哪、边界是什么、往年怎么考。**

它不是一张节点连线的炫酷大图，而是解决三个实际问题的**考点地图 + 索引**：
- 教师说"出 AVL 的题"，系统知道 AVL 在哪、有哪些子考点；
- 出题时锁定考点边界（`should_be`/`should_not_be` 来自这里）；
- 找参考题时按知识点过滤。

**三层来源（由粗到细）：**

```
第①层 考试大纲(dagang.md) —— 顶层结构
       2025 408 大纲：四科目分值、题型结构
        │ 细化
        ▼
第②层 四科目知识点库(kg/*.md) —— 主体内容
       按 "章 > 节 > 知识点 > 叶子属性" 层级组织
       粒度到"可出题的概念/结构/操作/机制/计算任务/边界条件"
        │ 锚定
        ▼
第③层 知识点标签(target_family) —— 索引键
       形如 "DS-5 > 树与二叉树 > 平衡二叉树"
       题库真题、题位经验卡都挂这个标签 → 反向索引
```

**关键设计：只存知识点名词和属性，不写定义、公式、组合方式。** 原因：知识图谱是给出题系统看"考点边界"的，不是给学生背的教材。写满定义反而会诱导模型抄图谱、不出新题。

**三级检索体系（按精度从高到低降级）：**

```
第①级 标签精确命中（首选，O(1)，无 LLM）
  教师说"AVL" → 立刻命中所有标了 AVL 的往年题
        │ 查不到时降级
        ▼
第②级 grep 关键词检索（兜底）
  LLM 生成关键词 → Python grep 扫题库全文 → LLM 归纳考察模式
        │ 仍查不到
        ▼
第③级 启发式兜底（题位经验卡 + 考察模式推断）
  保证出题流程不因"查不到"而中断
```

> **知识图谱管"考什么"（边界），K 雷达管"多难"（标尺）。两者汇入设计卡，把"考什么、多难、参考谁"全部钉死成客观约束。**

## 机制五 · 带路由的审核循环（治整体质量）

> **核心思想：审核不是简单的"通过/不通过"，而是按问题类型精准回退到正确的修复点，做最小修改而非整题重做。**

```
审核发现问题时，按问题类型路由回退：

题干漏洞       ──▶ 回 出题 重设题干      （不重写整题，只改题干）
代码建模错     ──▶ 回 写代码 修正 gen.py  （不动题干，只修代码）
文档抄写错     ──▶ 回 写文档 修正 solution（不动代码，只修文档）
措辞/格式问题  ──▶ 就地修正              （不回退，当场改）
```

**为什么必须带路由：** 不带路由的审核只有两个动作——"通过"或"整题重做"。整题重做既浪费（前面的好部分被丢掉），又容易引入新错误。带路由的审核做的是**外科手术式的最小修复**：哪里坏了修哪里，好部分保留。

> 这条机制本身不单独存在，它是对机制一、二、三、四的"执行纪律"——所有机制的判定结果（断言失败、K 值偏离、考点越界）最终都通过带路由的回退来落地修复。

# 第三部分 · 贯穿全局的两条"灵魂"

前述五大机制是"部件"，下面两条是让部件协同运转的"灵魂"。**这两条是项目最新的设计演进，也是最能体现设计思想深度的地方。**

---

## 灵魂一 · 确定性原理：题干自洽 × 建模可行 = 答案确定

> 这是审核机制的哲学根基，回答了一个根本问题：**在"无标准答案参照"的自动出题场景下，凭什么相信生成的答案是对的？**

### 困境：审核无法直接判"答案对错"

自动出题没有标准答案。更棘手的是——**一个自洽但版本错误的答案，会通过任何"一致性检查"**。比如补码除法，"恒置1法"和"恢复余数法"都能算出一个自洽的结果，但它们不一样。审核怎么判？

### 突破：把"难以验证的答案正确性"转化为"可验证的两个前置正确性"

> **确定性答案 = 题干自洽 × 建模可行**

Code as Truth 保证了：给定正确建模，`gen.py` 的 exec 输出就是确定答案。所以：

- **不审"答案对错"**——它无法直接判（无标准答案参照，自洽但错版本的答案会通过任何一致性检查）。
- **审两个前置正确性：**
  1. **题干自洽**（输入正确）：知识点无冲突、参数不耦合、条件自洽、符合设计卡要求。
  2. **建模可行**（过程正确）：按这个建模思路，步骤走得通、变量对、逻辑链完整。
- **答案正确性是这两个的自动推论**（exec 保证），不在审核范围。

```
            题干自洽 ──┐
                       ├──▶ 答案确定（由 exec 保证）
            建模可行 ──┘
                       
   审核只审前置两项 ──┬──▶ 审1·审输入自洽性（出题后、求解前）
                      └──▶ 审2·审过程可行性 + 结果与题干合围（求解后）
```

### 这条原理带来的审核架构：双点审核（审输入 vs 审过程）

两个审核点各管一头，互不重叠：

| 审核点 | 审什么 | 何时做 | 红线（不审什么） |
|--------|--------|--------|----------------|
| **审1（审题干）** | 输入自洽：知识点无冲突、参数不耦合、条件自洽、符合设计卡 | 出题后、求解前 | 不审答案（此阶段无解）；不判算法版本对错 |
| **审2（审求解）** | 过程可行 + 结果与题干合围 | 求解后 | **明令禁止判断"版本是否最优/唯一正确"**；不重跑 exec |

**审2 的"合围"判据（防止纠结的关键）：** 当 exec 结果与题干无法同时成立时，判矛盾来源是 A 还是 B：
- **A 参数缺陷**：算法本应合围却没合围（输入参数选得不好）→ 回 出题 改参数。
- **B 设问问题**：算法固有特性导致（如恒置1法精度损失）→ 回 出题 改设问措辞或换算法。

> 判 A/B 是"找矛盾来源"（算法特性 vs 参数），不是"裁版本对错"——这正是它**不会触发歧义纠结**的原因。这是整个审核架构不崩盘的关键纪律。

### 这条原理的实证威力

补码除法这类"有版本歧义的算法题"，曾经让求解智能体的 reasoning 飙到 **89064 字撑爆、零产出**。根因不是任务本身难，而是**系统性不确定性**（模型在多个教材版本间横跳 7 次无法裁定）。确定性原理 + 消歧（见下）把 reasoning 砍到 **24921 字（-72%）**，两轮产出正确结果。

---

## 配套：write_gen 消歧 —— 系统性不确定性治理

> 确定性原理要求"建模可行"，但"有版本歧义的算法"会让模型在版本间反复横跳、巨想崩溃。消歧是让建模可行的前置手段。

**根因（已实证）：** 补码除法在不同教材有多版本（n步/n+1步、恒置1/余数恢复、符号位单独定/首商即符号），模型横跳无法裁定唯一正确版本 → 反复重算验证 → reasoning 撑爆。

**解法（消歧三步）：**
```
write_gen 拿到题目
  ① 判断：题目是否有版本歧义？无 → 直接建模
  ② 消歧：从 design_card 读参考题路径 → 拉往年题的解题轨迹（自洽）
           → 照参考题演示的算法版本定版本（方法锁定）
  ③ 兜底：拉不到参考题时，自己选一个版本，gen.py 顶部声明 VERSION 标记
           → 不纠结，直接写码 → 交付时标注"此处为模型自定版本，请人工复核"
```

**关键纪律：**
- 方法锁定后不重选版本、不在 reasoning 里重推算法、不手算验证（exec 会验）。
- **消歧信息必须自洽**——矛盾示例反而会制造新纠结（实证：矛盾示例让模型花 5 万字校验矛盾）。

> **确定性原理 + 消歧，是把"审核"从"判答案对错"的死胡同，提升到"判前置正确性"的可工程化层面。** 这是审核机制最新的、也是最重要的理念升级。

---

## 灵魂二 · 模型驱动收敛：从"规则拦截"到"模型自主判断"

> 这是交互层（需求澄清层）的设计哲学，回答了：**怎么把教师模糊的出题需求，可靠地收敛成后端可执行的最小需求文档？**

### 旧路的局限：规则拦截（micromanagement）

传统的做法是"后端正则拦截 + 硬编码追问话术 + SKILL.md 固定步骤（Step1→2→3）"。问题：
- 追问话术僵化，无法适应千变万化的真实需求；
- 固定步骤是**微管理（micromanagement）**——告诉模型每一步做什么，扼杀了模型自身的判断力；
- 场景被当成固定标签（"场景A/B/C"），而非对当前上下文的动态判断。

### 新路：模型驱动收敛（empowerment）

> **核心原则：告诉模型"你能做什么、你要达到什么、边界在哪"，让它自己规划路径。**

**多轮候选收敛模型——每轮只缩小一个维度：**

```
用户: "我想出数据结构期末卷"

═══ Round 1: 范围收敛（用模型参数知识，不调工具）═══
Agent: "通常覆盖：线性表、栈队列、树、图、查找、排序。
        全覆盖，还是重点考某几块？"
用户: "重点考树、图、排序"

═══ Round 2: 题型结构收敛（用模型参数知识）═══
Agent: "常规期末卷、考研风格，还是算法实践风格？
        常规期末卷通常 8-12 题，选择+填空+简答+算法混合。"
用户: "常规期末卷，10题"

═══ Round 3: 具体考法收敛（调工具检索）═══
Agent: grep_search(["二叉树遍历","图的DFS","排序算法"], max_results=30)
Agent: 归纳候选考法，给出推荐方案
用户: "按推荐"

═══ Round 4: 生成草案让用户批注（调工具）═══
Agent: write_file 草案 → 教师批注 → 交付出题团队
```

**四条关键原则：**
1. **粗粒度用模型知识**：第一二轮不调工具，直接用模型参数知识（快）。
2. **细粒度用工具检索**：第三轮开始 grep_search / 读知识图谱（准）。
3. **模型自主决策**：不硬编码"Step N 必须调 grep_search"，让模型判断何时该检索。
4. **每轮只缩小一个维度**：范围 → 题型 → 考法 → 草案，避免一次性追问所有字段把用户压垮。

### 赋能而非微管理：给模型的五类信息

```
1. 环境能力（Environment）—— 你有哪些工具、能访问哪些数据
2. 目标（Goal）—— 把模糊需求收敛为"题型+知识范围+考察方式"的最小需求文档
3. 规则与边界（Rules）—— 不编造知识点/K-radar；每轮只收窄一维；默认值只能作推荐
4. 理念（Philosophy）—— 粗粒度用参数知识，细粒度调工具验证；先给候选让用户选
5. 行为控制（Behavior）—— 简单问题快回答，复杂问题才深思考（思考预算分配）
```

**不应该给模型的（微管理反例）：**
- ✗ 固定步骤："Step 1 做 X，Step 2 做 Y"
- ✗ 场景锁定："场景 C 必须两轮迭代"
- ✗ 工具调用强制："场景 B 第一步必须 grep_search"

### 收敛完成判据：handoff 的三个要素

每个题位至少具备三要素后，才能交接给出题团队：

```yaml
Q1:
  question_type: 选择题          # 要素1: 题型
  knowledge: 二叉树遍历           # 要素2: 知识范围
  examination_focus: 遍历序列推导  # 要素3: 考察方式
```

只有 `knowledge: 树`（范围太粗）时，还不能进入出题——必须继续收敛到具体考察方式。

> **模型驱动收敛，是把交互层从"僵化的规则引擎"升级为"会判断的协作者"。** 它信任模型的能力，只在边界上设护栏，而不是在每一步上系鞋带。

# 第四部分 · 设计哲学总结：四条贯穿始终的原则

把前面所有机制抽象到最高层，整个项目的设计理念可以归结为四条原则：

## 原则一：不靠模型自觉，靠机制和数据兜底

> 三大顽疾的共同根因是"LLM 靠脑内推理出题 + 审题，错的地方恰是它最自信的地方"。
> 所以我们的每一个机制，本质都是在**把"模型自觉"替换成"机器可检的客观判据"**：
> - 数值对不对 → 不靠模型"觉得对"，靠 exec 跑一遍（Code as Truth）；
> - 考点考没考到 → 不靠模型"声称考了"，靠 assert 检出（可证伪断言）；
> - 难度够不够 → 不靠模型"觉得中等"，靠 K 雷达落在锚点范围内（认知雷达）；
> - 答案可信不可信 → 不靠"看起来自洽"，靠题干自洽 × 建模可行两个前置条件（确定性原理）。

## 原则二：把"不可验证"转化为"可验证的前置条件"

> 这是确定性原理的精髓，也是整个审核体系能成立的原因。
> 直接判"答案对错"是死路（无标准答案、自洽但错版本能蒙混过关）。所以我们不审答案，**审答案成立所依赖的两个前置条件**（题干自洽、建模可行），让答案正确性成为它们的自动推论。
> 这个思路同样体现在交互层：不直接生成最终需求，而是通过每轮收窄一个维度的多轮收敛，让"需求是否充分"变成可判断的（三要素是否齐全）。

## 原则三：赋能而非微管理

> 这是模型驱动收敛的精髓，也是 Prompt 设计的统一哲学。
> 给模型"能力 + 目标 + 规则"，让它自己规划路径，而不是告诉它每一步做什么。这条原则从交互层（不硬编码追问步骤）延伸到出题层（design_card 是"宪法"，下游只"实现"不"推翻"，具体怎么实现交给模型）。
> 信任模型的能力，只在边界上设护栏。

## 原则四：最小修复，外科手术式回退

> 带路由的审核循环体现了这条原则：哪里坏了修哪里，好部分保留。
> 题干坏改题干、代码错改代码、文档抄错改文档、措辞问题就地改——绝不整题重做。这既省成本，又避免引入新错误。
> 它的前提是前述机制把"问题"定位到了足够细的粒度（断言告诉你考点没覆盖、K 雷达告诉你难度偏离、A/B 判据告诉你矛盾来自参数还是设问）。

# 附：设计理念的"机制—顽疾—原则"对照总表

| 设计机制 | 治什么顽疾 | 体现哪条原则 | 一句话 |
|---------|-----------|-------------|--------|
| Code as Truth | 事实性错误 | 原则一（不靠自觉） | 数值让代码算，模型只写代码、抄结果 |
| 可证伪断言 | 题干漏洞 | 原则一 | 把"考什么"翻译成可机器检出的 assert |
| K1–K5 认知雷达 | 难度偏离 | 原则一 | 把"难度"拆成五维可量化、可检索的量 |
| 知识图谱 | 考点跑偏 | 原则一 | 把大纲变成可检索、可注入的考点结构树 |
| 带路由的审核循环 | 整体质量 | 原则四（最小修复） | 按问题类型精准回退，不整题重做 |
| **确定性原理**（审核灵魂） | 审核可信度 | 原则二（转化可验证） | 题干自洽 × 建模可行 = 答案确定，审前置不审答案 |
| **模型驱动收敛**（交互灵魂） | 需求不可靠 | 原则三（赋能） | 给能力+目标+规则，让模型自主规划收敛路径 |

## 与顶层愿景的关系

这些机制和原则，服务于项目的长期愿景（详见 `docs/408_adaptive_question_generation_design.md`）：

> 项目长期目标不是构建解题模型，而是构建面向 408 考研学习场景的**自适应训练系统**。解题只是中间能力，**出题、诊断用户能力缺口、生成恰好卡在能力边界上的个性化题目**才是最终目标。

当前的设计机制解决的是"出题"这一环的可靠性。后续工作将在此基础上接入用户画像、能力诊断与个性化出题闭环——但无论后续如何演进，"不靠模型自觉、靠机制兜底"这条底色不会变。

---

> **一句话收尾：我们不是在"让 LLM 出题"，而是在"为 LLM 搭一套让它不得不靠谱的机制"。** 机制的每一个设计，都是对 LLM 某一类天然缺陷的对症下药。
