# Q45 概念题组——银行家算法与安全状态 · 解析

---

## 第 1 题

**答案：B**

**解析：**

逐条分析三个论断：

- **I 正确。** 安全状态的定义是"存在一个安全序列，使所有进程都能按某种顺序获得资源并顺利完成"。既然存在这样的完成序列，系统就一定不会死锁。因此安全状态 → 一定无死锁。

- **II 错误。** 不安全状态意味着"当前不存在安全序列"，但这并不等于系统一定会死锁。不安全状态只表示系统**有可能**进入死锁——取决于后续各进程的实际资源请求和释放行为。如果后续进程恰好没有进一步请求资源就释放了已占资源，系统仍可能正常运行而不发生死锁。将"不安全"等同于"一定死锁"是最常见的概念混淆。

- **III 正确。** 死锁意味着所有进程都无法继续推进，不可能存在任何安全序列，因此死锁状态一定是不安全状态。换言之，安全状态是无死锁的充分条件，不安全状态是死锁的必要条件。

综上，I 和 III 正确，II 错误，选 **B**。

> **干扰项分析：**
> - 选 A（仅 I）：遗漏了 III。死锁一定是不安全状态，这也是正确的推论。
> - 选 C（II 和 III）：II 是错误的。不安全状态不等于死锁，只是有可能发展为死锁。
> - 选 D（I、II、III）：II 错误，不安全状态不一定会发生死锁。

## 第 2 题

**答案：A**

**解析：**

银行家算法处理资源请求时的完整流程如下：

1. **检查 Request_i ≤ Need_i**：确认请求量不超过该进程声明的最大需求量。若超过，说明进程请求有误，报错。
2. **检查 Request_i ≤ Available**：确认系统当前有足够的可用资源。若不足，进程必须等待。
3. **试探性分配**：假定批准该请求，从 Available 中扣除 Request_i，将其加入 P_i 的 Allocation，并从 P_i 的 Need 中扣除。
4. **执行安全性算法**：在试探性分配后的状态下，检查系统是否仍处于安全状态。
5. **判定**：若安全，正式确认此次分配；若不安全，回滚试探性分配，拒绝请求，P_i 等待。

因此正确顺序为：**Request_i ≤ Need_i → Request_i ≤ Available → 试探性分配 → 安全性算法 → 正式批准/拒绝**，选 **A**。

> **干扰项分析：**
> - 选 B：两步检查的顺序颠倒。虽然从结果看两步都需通过，但标准流程要求先检查 Request ≤ Need（验证请求合法性），再检查 Request ≤ Available（验证资源充足性）。先检查 Available 是不规范的。
> - 选 C：安全性算法应在试探性分配之后执行，而非在 Request ≤ Available 之前。安全性算法需要基于分配后的状态运行。
> - 选 D：安全性算法是对试探性分配后的状态进行检查的，不应在请求合法性检查之前运行。

## 第 3 题

**答案：A**

**解析：**

银行家算法中安全性算法的核心步骤：

1. **初始化**：Work = Available（Available 的副本），Finish[i] = false（所有进程标记为未完成）。
2. **逐轮扫描**：找到一个满足 Finish[i] = false **且** Need_i ≤ Work 的进程 P_i。
3. **更新**：将 P_i 的 Allocation_i 加入 Work（Work = Work + Allocation_i），标记 Finish[i] = true，表示 P_i 可完成并释放其全部资源。
4. **判定**：若所有 Finish[i] = true，则系统处于安全状态，已扫描的进程完成顺序构成一个安全序列；若找不到任何可满足的进程但仍有未完成进程，则系统处于不安全状态。

关键理解：Work 增加的是**已完成进程的已分配资源（Allocation）**，因为进程完成后会释放它持有的全部资源。Need 是尚需资源量，不应加入 Work。初始值是 Available 而非各类求和。

选 **A**。

> **干扰项分析：**
> - 选 B：Finish 初始值应为 false（表示尚未完成），而非 true。加入 Work 的应是 Allocation 而非 Need。判定条件应全部为 true 而非 false。
> - 选 C：Work 的初始值应为 Available 向量，而非所有进程 Allocation 之和。加入 Work 的应是 Allocation 而非 Need。
> - 选 D：Work 初始值应为 Available 而非 Need 之和；扫描条件应是 Need_i ≤ Work 而非 Max_i ≤ Work（Max 包含已分配部分，不能直接与 Work 比较）。

## 第 4 题

**答案：D**

**解析：**

题目要求选出**错误**的叙述。

- **A 正确。** Need 矩阵的定义就是 Need[i][j] = Max[i][j] − Allocation[i][j]，表示进程 i 对资源 j 的尚需量。

- **B 正确。** Request_i ≤ Need_i 通过表示请求合法（未超过最大需求），但 Request_i ≤ Available 未通过表示系统当前可用资源不足。此时进程 P_i 必须等待，系统不分配资源。这是银行家算法的标准行为。

- **C 正确。** 试探性分配后需通过安全性算法判定：安全则确认分配（因为存在安全序列，所有进程可顺利完成）；不安全则回滚（因为继续分配可能导致死锁）。

- **D 错误。** 通过了 Request_i ≤ Need_i 和 Request_i ≤ Available 两步检查，**只说明请求本身合法且资源暂时够用**，但并不保证分配后系统仍处于安全状态。必须在试探性分配后执行安全性算法，确认安全后才能正式批准。跳过安全性算法直接分配，正是银行家算法要避免的——可能导致系统进入不安全状态甚至死锁。

因此，**错误的叙述是 D**。

> **干扰项分析：**
> - A、B、C 均为正确叙述，D 的错误在于忽略了安全性算法这一关键步骤。这是"条件遗漏"型干扰——考生可能认为"请求合法 + 资源够用 = 可以分配"，但银行家算法的核心正是第三步安全性检查。
