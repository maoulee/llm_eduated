## 考点
- **核心考点**：循环队列的入队/出队操作的代码实现（判空、判满、front/rear 指针更新）
- **考察侧重点**：
  - 入队操作：判满条件（`(rear+1)%MaxSize == front`）、rear 指针更新（`rear = (rear+1)%MaxSize`）
  - 出队操作：判空条件（`front == rear`）、front 指针更新（`front = (front+1)%MaxSize`）
  - 循环队列"牺牲一个存储单元"的判满约定
  - 取模运算在环形结构中的作用

## 难度目标
- **K1=2（较低）**：需记忆循环队列的基本定义（front/rear 含义、判空判满约定），但题干给出函数框架和变量含义，概念模糊也能顺着代码逻辑填空
- **K2=3（标准）**：需正确写出取模运算表达式，涉及非 2 的幂次（MaxSize 可能非 2 的幂）的取模计算，填空语句本身即是计算表达式的构建
- **K3=2（较低）**：填空题，每空仅需 1-2 步逻辑推导（如：入队时先判满→更新 rear），路径唯一
- **K4=2（较低）**：循环队列的"牺牲一个单元判满"是 408 常规知识点，考生基本不会踩坑；题干若明确标注判满约定则陷阱更少
- **K5=1（微弱）**：单一知识点内部解决，不涉及其他子系统

## 考察模式
**代码补全型——循环队列操作实现**
- 选择理由：与 slot 的 examination_mode 一致，符合 408 综合题中数据结构代码填空的常见考法
- 参考历史经验：2011 年和 2014 年真题均涉及队列/栈操作代码，循环队列的判空判满和指针更新是高频考点
- 模式要点：题干给出 C 语言风格的入队/出队函数框架，关键语句用空格代替（通常 4 个空，对应入队的判满+rear更新、出队的判空+front更新），学生填写正确语句

## 出题要求
- **题型**：综合题（代码填空）
- **总条件数**：约 3-4 个显式条件
  - 条件 1：队列结构体定义（含数组、front、rear 字段）
  - 条件 2：队列最大容量 MaxSize 的值（用于取模）
  - 条件 3：函数框架（含函数签名、已有语句、空格标注）
- **条件设计原则**：
  - 结构体定义应完整，让学生清楚各字段含义
  - 函数框架应保留部分语句（如入队的 `Q->data[Q->rear] = x;`），仅空出判空/判满和指针更新语句
  - 判满约定（牺牲一个单元）可在题干中说明，或让学生自行判断
- **参数取值范围要求**：
  - MaxSize 可取任意正整数（≥3），Question Agent 自定，但建议避免太小的值（如 2），以保证判满逻辑有意义
  - front 和 rear 的初始值（通常均为 0）应在题干中给出

## 子问题规划
本题为代码填空综合题，以"多个空格"的形式组织，建议 **4 个空格**，对应以下考察点：

| 空格 | 所在函数 | 考察目标 | 分值 | 关系 |
|------|---------|---------|------|------|
| 空1 | 入队函数 | 判满条件 | 1分 | 独立 |
| 空2 | 入队函数 | rear 指针更新 | 1.5分 | 依赖空1（逻辑上先判满后更新） |
| 空3 | 出队函数 | 判空条件 | 1分 | 独立 |
| 空4 | 出队函数 | front 指针更新 | 1.5分 | 依赖空3（逻辑上先判空后更新） |

- **空1 与空2 串行**（同一入队函数内，先判满再更新 rear）
- **空3 与空4 串行**（同一出队函数内，先判空再更新 front）
- **入队组与出队组并列**（两个独立函数，无数据依赖）

## 参数约束
- **MaxSize**：正整数，建议范围 [5, 50]，Question Agent 自定具体值；不要求为 2 的幂
- **front 初始值**：通常为 0，题干给出
- **rear 初始值**：通常为 0，题干给出
- **判满约定**：牺牲一个存储单元（即队满条件为 `(rear+1)%MaxSize == front`），这是 408 标准约定
- **取模运算**：所有指针更新必须使用 `% MaxSize`，不可省略
- **一致性约束**：MaxSize 的值必须与函数框架中的取模表达式一致

## 参考经验
- **历史模式**：2011_Q3 和 2014_Q3 均以代码实现为载体考查队列/栈操作，强调判空判满和指针移动的核心逻辑
- **难度锚点**：代码填空题 K2=3（需正确构建取模表达式）、K3=2（每空逻辑简单）、K4=2（"牺牲一个单元"是常规注意点），与 slot 的 k_radar 一致
- **典型陷阱**：
  1. 判满时忘记取模（写 `rear+1 == front` 而非 `(rear+1)%MaxSize == front`）
  2. 判满条件用 `rear == front`（与判空混淆）
  3. 指针更新先加再赋值 vs 先赋值再加（取决于 front/rear 约定）
  4. rear 指向队尾元素的下一个位置 vs 指向队尾元素本身（影响判满条件写法）
