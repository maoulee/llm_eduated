# 断言与 Code as Truth —— 用一道题讲透两个核心机制

> 本文档用一个**完整的真实例子**讲清两件事：
> 1. 什么是 **断言（assert）**？
> 2. 什么是 **Code as Truth（代码即真相）**？
>
> 选例子：AVL 树连续插入后的平衡辨析（项目里 `TEST_AVL` 的真实场景，也是 408 常考题型）。
> 我们会先看"没有这两个机制时模型怎么出错"，再看"有了它们如何被兜住"。

---

## 0. 先看题目本身

> **题干：** 依次将关键字 `30, 20, 10, 25, 40` 插入初始为空的 AVL 树。
> (1) 给出调整过程中触发的旋转类型。
> (2) 给出最终树的形态。
> (3) 判断最终树是否平衡。

这道题考的是 AVL 的**旋转辨析 + 平衡维护机制**，属于机制推演型（K3 主导）。看起来不难，但它恰恰是模型最容易"算错一步、后续全错"的题型。下面来看看为什么。

---

## 1. 没有机制时：模型怎么出错

如果让 LLM **纯靠脑内推理**做这道题，常见错误有三类：

### 错误一：数值算错（多步推演断链）

```
模型脑内推演（错的版本）：
  插入 30,20,10 → 30 失衡(LL) → 右旋 → 20 成根    ✓ 正确
  插入 25        → 树: 20 根，左 10，右 30          ✓ 正确
  插入 40        → 挂到 30 右子，未失衡             ✓ 正确
  ── 到这里都还对 ──
  
  然后模型"回忆"旋转类型时说：
  "插入 25 时触发了 RL 旋转"      ✗ 错！25 插入时根本没失衡
  "插入 40 时触发了 RR 旋转"      ✗ 错！40 插入后 30 没失衡
```

**根因：** 前几步对，但"有没有失衡、失衡是哪种"这种**判断**，模型靠"印象"而非真实计算，错的地方恰是它最"确信"的地方。一旦它"觉得"应该有旋转，就会编出一个。

### 错误二：旋转类型记混

```
模型可能把"右旋"和"右子树的右旋(RR情况)"记混：
  "30 失衡，是 RR 情况，做右旋"   ✗ 错！30 的失衡是 LL 情况，做右旋
                                   （结论"右旋"对，但"RR情况"是瞎说的）
```

**根因：** LL/LR/RL/RR 四种旋转的判断条件和方向容易混淆，模型靠记忆而非规则推演。

### 错误三：最终形态编造

```
模型给出的"最终树"：
  "根 20，左子 10，右子 30，30 的左右分别是 35 和 40"
                                      ✗ 错！35 从哪来的？题里没有 35
```

**根因：** 模型在长推演后"补全"细节，凭空生成不存在的结点。

> **这三类错误的共同点：全部发生在模型的"脑内"。** 你无法验证它推理过程对不对，只能看个结果，结果错了也不知错在哪。**这是"脑内推理"的天然缺陷。**

## 2. 什么是 Code as Truth（代码即真相）

### 一句话定义

> **凡涉及数值、状态、结构的内容，一律由可执行代码算出来，LLM 只负责"写代码"和"抄写结果"，绝不"脑内计算"。代码跑出什么，真相就是什么。**

### 落到这道题上

模型不再"脑内推演 AVL"，而是**写一段真实的 Python**，让机器去算：

```python
# gen.py —— 模型写的（code as truth）
class Node:
    def __init__(self, v):
        self.v = v
        self.left = None
        self.right = None

def height(n):           # 算高度
    return 0 if n is None else 1 + max(height(n.left), height(n.right))

def balance_factor(n):   # 算平衡因子
    return 0 if n is None else height(n.left) - height(n.right)

# ... insert 完整实现（含四种旋转）...
```

然后**真实运行**它：

```python
root = None
for v in [30, 20, 10, 25, 40]:
    root = insert(root, v)
    print(f"插入 {v} 后，旋转记录: {rotations}, 是否平衡: {is_balanced(root)}")
```

**机器算出来的真实输出（这不是模型"说"的，是代码"跑"出来的）：**

```
插入 30 后，旋转记录: [],     是否平衡: True
插入 20 后，旋转记录: [],     是否平衡: True
插入 10 后，旋转记录: [('LL', 30)],  是否平衡: True    ← 唯一一次旋转
插入 25 后，旋转记录: [('LL', 30)],  是否平衡: True    ← 没有新旋转
插入 40 后，旋转记录: [('LL', 30)],  是否平衡: True    ← 没有新旋转
```

**最终树的形态（代码 traverse 出来，不是模型画的）：**
```
        20
       /  \
     10    30
          /  \
         25   40
```

### 为什么这就是"真相"

| | 脑内推理 | Code as Truth |
|---|---------|---------------|
| 谁在算 | 模型"想" | **机器算** |
| 能否验证 | 不能，只看个结果 | **能，跑一遍就知道** |
| 错在哪 | 查不出 | **代码每一步都可查** |
| 出错了 | 模型还"很确信" | **assert 失败立刻报错** |
| 35 从哪来 | 模型"补"出来的 | **代码里根本没有这个值** |

> **关键纪律：文档智能体只"忠实抄写"代码跑出的结果，禁止重新计算。** 抄错容易查（对照 exec 输出），但"算错"查不出——所以宁可抄，不要算。审核智能体也对照代码核查，**不在脑内重算**。

## 3. 什么是断言（assert）

### 一句话定义

> **断言 = 一个能被机器自动检查的"通过条件"。它声明：题目成立，当且仅当某个客观特征被满足；不满足就立刻报错。**

### 为什么需要断言

回到第 1 节"模型怎么出错"。问题不只是"算错了"，还有更隐蔽的一类：

> **模型可能出一道"怎么答都算对"的坏题。**

比如这样一道"AVL 辨析题"：

> ~~题干：将 `30,20,10,25,40` 插入 AVL 树，问"最终的树是否平衡"。~~
> ~~通过条件：树保持平衡。~~

这题有什么问题？——**零次旋转，树本来也平衡。** 所以这道题考没考"旋转辨析"？**没考。** 学生写"平衡"就对，写"不平衡"就错，但整道题根本没触发任何旋转，所谓的"辨析"是个空壳。

**断言就是用来堵这种漏洞的。** 题干必须声明一个**可证伪**的通过条件，并对应到代码里的 `assert`：

### 断言的样子

```python
# 断言1：本题必须至少触发 1 次旋转（否则没考旋转辨析）
#         ↑ 如果出题时参数选成"不触发任何旋转"，这个 assert 立刻挂
assert len(rotations) >= 1, f"题目声称考旋转辨析，但实际触发了 {len(rotations)} 次旋转"

# 断言2：触发的必须是 LL 类型（题目本考 LL 辨析）
assert rotations == [('LL', 30)], f"旋转记录不符: {rotations}"

# 断言3：最终树必须平衡（AVL 的根本性质）
assert is_balanced(root), "AVL 树插入后不平衡"

# 断言4：最终根必须是 20（由 LL 旋转得出）
assert root.v == 20, f"最终根应为 20，实际 {root.v}"

# 断言5：结点数 = 插入数（不能凭空多出结点）
assert count_nodes(root) == 5, f"结点数应为 5，实际 {count_nodes(root)}"
```

### 断言的三个关键性质

```
┌──────────────────────────────────────────────────────┐
│  一个合格的断言必须满足三点：                            │
│                                                      │
│  ① 存在性    题干必须声明通过条件，不能"考啥都行"       │
│                                                      │
│  ② 可证伪性  必须能检出"没满足"的情况（这是关键！）     │
│              否则它就是个恒真的废判据                  │
│                                                      │
│  ③ 覆盖性    断言要覆盖题目声称的考点                   │
│              "考旋转"就必须 assert 旋转次数 ≥ 1        │
└──────────────────────────────────────────────────────┘
```

**反例（废断言，必须被审核拦截）：**
```python
# 废断言：树保持平衡
assert is_balanced(root)
# 这对任何合法的 AVL 插入都成立 → 检不出"没考旋转" → 等于没断言
```

**正例（好断言）：**
```python
# 好断言：锁定考点
assert len(rotations) >= 1   # 锁定"考了旋转"这个考点
```

## 4. 两个机制怎么配合（核心图）

断言和 code-as-truth 是**配合关系**：代码提供真相，断言守住质量。

```
                    ┌─────────────────────────────────┐
                    │         题干 (design)            │
                    │  声明通过条件(可证伪、覆盖考点)    │
                    └────────────┬────────────────────┘
                                 │
                ┌────────────────┴────────────────┐
                ▼                                  ▼
    ┌───────────────────┐              ┌─────────────────────┐
    │  ① Code as Truth  │              │  ② 断言 (assert)     │
    │  写 gen.py        │   代码跑出    │  把"通过条件"翻译成   │
    │  ↓ exec 运行      │ ───────────▶ │  机器可检的 assert   │
    │  得到真实数值/状态 │   真相         │  ↓ 逐条核对          │
    └───────────────────┘              │  pass / fail        │
                                       └─────────┬───────────┘
                                                 │
                                    ┌────────────┴────────────┐
                                    │ fail                    │ pass
                                    ▼                         ▼
                          ┌──────────────────┐      ┌──────────────────┐
                          │  路由回退修复      │      │  题目成立         │
                          │  题干坏 → 重设题干 │      │  答案可信         │
                          │  代码错 → 修 gen  │      │  考点被真实覆盖   │
                          └──────────────────┘      └──────────────────┘
```

**用一句话说清分工：**

| 机制 | 解决什么问题 | 怎么解决 |
|------|------------|---------|
| **Code as Truth** | 事实性错误（算错、幻觉） | 让**代码**算，不让模型脑内算 |
| **断言** | 题干漏洞（考点没被真实触发） | 用**可证伪的 assert** 锁定考点 |

## 5. 完整对照：同一道题，三个版本

### 版本 A：纯脑内推理（典型错误）

```
模型答：(1) LL 旋转 + RL 旋转 + RR 旋转（共 3 次）   ✗
        (2) 根 20，右子 30，30 的左右是 35 和 40      ✗ (35 凭空)
        (3) 平衡                                      ✓ (蒙对)
```
**问题：** 全靠模型"想"，无法验证，错了查不出。

### 版本 B：Code as Truth 但无断言

```
模型写代码，exec 跑出真实结果：
  (1) LL 旋转 1 次                                   ✓
  (2) 根 20，右子 30，30 的左右是 25 和 40            ✓
  (3) 平衡                                          ✓
```
**进步：** 数值正确了。**但有个隐患**——如果当初出题时参数选成 `10,20,30,40,50`（根本不触发失衡的序列），代码也能"成功跑完"，却考了个寂寞。**没有断言，挡不住"题目成立但没考到点"。**

### 版本 C：Code as Truth + 断言（我们的做法）

```
模型写代码，exec 跑出真实结果（同上）                  ✓
然后断言逐条检查：
  assert len(rotations) >= 1     ✓  锁定考点：确实考了旋转
  assert rotations == [('LL',30)] ✓  锁定考法：考的是 LL
  assert is_balanced(root)       ✓  AVL 根本性质
  assert root.v == 20            ✓  旋转结果正确
  assert count_nodes(root) == 5  ✓  无凭空结点
全部 pass → 题目成立、答案可信、考点被真实覆盖
```
**这才是闭环：** 数值由代码保证正确，考点由断言保证覆盖。两个机制缺一不可。

## 6. 那个"废题"是怎么被挡住的（断言的真实威力）

最能体现断言价值的，是它**拦截坏题**的能力。假设出题智能体一时手滑，出了这样一道题：

> 题干：将 `10, 20, 30, 40, 50` 插入 AVL 树，问旋转类型。
> （隐含问题：这个序列会触发多次旋转，但题干没说清要答哪几次）

代码跑起来：
```python
rotations = []
for v in [10,20,30,40,50]:
    root = insert(root, v)
# 实际 rotations = [('RR',10), ('RR',10), ('RR',20)]  （触发 3 次 RR）
```

断言登场：
```python
assert rotations == [('LL', 30)]   # ← 题干预期 LL，实际是 3 次 RR
# AssertionError: 旋转记录不符: [('RR',10),('RR',10),('RR',20)]
```

**断言失败 → 触发回退**：要么题干的预期错了（重设题干），要么代码算错了（修 gen.py）。**审核根据路由决定回退到哪个环节。**

> 这就是断言的本质价值：**它不是"检查答案对不对"，而是"检查这道题到底考没考到它声称要考的东西"。** 没有它，模型会出大量"看着像题、实际没考到点"的空壳题。

---

## 7. 总结

| | 断言 (assert) | Code as Truth |
|---|---------------|---------------|
| **是什么** | 可机检的"通过条件" | 代码算出真相，模型只抄不算 |
| **解决什么** | 题干漏洞（考点没被真实触发） | 事实性错误（数值算错、幻觉） |
| **核心手段** | 把"考什么"翻译成 `assert`，可证伪 | 让 `gen.py` 跑出客观结果 |
| **失败时** | 报错 → 带路由回退修复 | 报错 → 修 gen.py |
| **配合关系** | 代码提供真相，断言守住质量，缺一不可 |

> **一句话：Code as Truth 保证"算得对"，断言保证"考得对"。**
> 前者治事实性错误，后者治题干漏洞。两个机制一起，把"靠模型自觉"变成"靠机制兜底"。
