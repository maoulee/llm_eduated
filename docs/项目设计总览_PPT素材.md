# 面向 408 考研的自适应出题系统 — 项目设计总览

> 本文档面向 PPT 演示，按 **「挑战 → 做法」** 的结构组织。
> 第一部分：出题的三类顽疾（我们要解决的问题）。
> 第二部分：我们的做法（架构、智能体职责、核心机制）。
> 所有内容均来自项目代码与设计文档，不含实现细节，可直接拆为幻灯片素材。

# 第一部分 · 出题面临的三大挑战

> 用 LLM 自动出题，看似简单，实则产出的题目"肉眼看着像题，仔细一查全是病"。
> 我们把顽疾归纳成三类：**题干漏洞、事实性错误、难度与内容偏离**。
> 这三类不解决，所谓"自动出题"产出的是**不可用的题**。

## 挑战一：题干漏洞（题目本身的逻辑不自洽）

**症状：题目能读懂，但"做不下去"或"答案不唯一"。**

题干存在结构性缺陷，导致学生无法作答，或怎么答都"对"。典型表现：

| 子问题 | 说明 | 举例 |
|--------|------|------|
| 参数互相矛盾 | 给定的参数在同一题里无法共存 | 位宽 8 位，却要求表示一个超出范围的数值 |
| 条件缺失或冗余 | 该给的条件没给，或给了用不上的废条件 | 算法题没说明输入规模；或塞了与本考点无关的干扰数据 |
| 隐含前提未声明 | 题目成立依赖某个前提，但没写出来 | 默认"单链表带头结点"，却没在题干说明 |
| **通过条件无法判定** | 题干没声明"什么样的结果算对" | **核心病**：AVL 题通过条件只写"树保持平衡"——零次旋转也满足，等于没考旋转辨析 |

> **为什么这类问题最致命：** 它不是"答案错"，而是"题目本身立不住"。学生再聪明也答不出一个坏题。这类问题靠人审耗时，靠模型自检往往会"自我感觉良好"放过。

## 挑战二：事实性错误（内容算错、记错）

**症状：题目没问题，但模型给出的参考答案 / 数值 / 机制是错的。**

LLM 在多步推理、数值计算上天然有"幻觉"，越长的推理链越容易错。典型表现：

| 子问题 | 说明 | 举例 |
|--------|------|------|
| 数值算错 | 多步串行计算中某一步出错，后续全错 | AVL 连续插入的平衡因子推演，第 3 步算错，整棵树后续全错 |
| 公式 / 定理记错 | 概念记忆不准，张冠李戴 | 把快排的 partition 逻辑套到归并排序上 |
| 机制误判 | 对底层运行机制的判断与实际不符 | 误判页面置换算法的实际淘汰顺序 |
| 推理链过长而断链 | 步骤越多，模型越容易在某步丢失状态 | 5 步以上的状态跟踪，模型常在第 4、5 步偏离 |

> **为什么这类问题难治：** 一次性"让模型解题并自检"是死循环——用会犯错的模型去检查它自己犯的错，错的地方往往恰是它最"确信"的地方。**靠脑内推理无法根治脑内推理的错误。**

## 挑战三：难度与内容偏离（出得"像题"，但不是"要的题"）

**症状：题目质量尚可，但跟教师的需求对不上。**

没有客观锚点时，"难度"和"考点"全凭模型主观判断，极易漂移。典型表现：

| 子问题 | 说明 | 举例 |
|--------|------|------|
| 难度跑偏 | 目标难度 3，却出成常识题（1）或偏怪题（5） | 要一道"标准中等题"，模型给出了一个冷门边界 case |
| 考点偷换 | 本来要考 A，模型顺手考成了 B | 本考"页面置换"，结果考成了"进程调度" |
| 风格不符 | 不贴合目标考试的出题风格 | 期末卷难度，却被换成了考研级；或反之 |
| 整卷重复 | 组卷时多道题考点 / 考法雷同 | 一张卷子里三道题都在考同一类陷阱 |

> **为什么这类问题普遍：** "中等难度""考机制"这类词是主观的、不可复现的。没有可测量的难度定义，就没有"是否达标"的判据。这是整条出题链路最缺乏"地基"的一环。

---

## 三类问题的共同根因

```
题干漏洞 ──┐
事实性错误 ─┼──→ LLM 出题缺乏"客观真相"和"可机检判据"
难度偏离 ──┘      靠脑内推理出题 + 审题，错的地方恰是它最自信的地方
```

**我们的核心思路就是给这三个根因分别对症下药**（见第二部分）。

# 第二部分 · 我们的做法

## 做法总览：三个对策，对症下药

| 挑战 | 根因 | 我们的对策 |
|------|------|-----------|
| 题干漏洞 | 题目缺可判定标准 | **可机检的"通过条件" + 题干审核** |
| 事实性错误 | 脑内推理会幻觉 | **Code as Truth：数值让代码算** |
| 难度内容偏离 | 难度无客观定义 | **K1–K5 认知雷达：难度可量化、可检索** |

下面分别展开，并给出整体架构草图与每个智能体的职责。

---

## 对策一：Code as Truth —— 把"算"交给代码（治事实性错误）

> **核心思想：凡涉及数值、状态、结构的内容，一律由可执行代码算出来，LLM 只负责"写代码"和"抄写结果"，不负责"脑内算"。**

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  题干        │ ──▶ │  求解智能体    │ ──▶ │  可执行代码    │
│ (question)  │     │ 写 gen.py    │     │  gen.py      │
└─────────────┘     └──────────────┘     └──────┬───────┘
                                                │ exec 跑出真实数值
                                                ▼
                                        ┌──────────────┐
                                        │  文档智能体    │
                                        │ 忠实抄写结果   │ ──▶ solution.md
                                        └──────────────┘
```

**关键纪律：**
- 代码是**唯一真相**。`gen.py` 跑出什么，答案就是什么。
- 文档智能体只做"忠实抄写"，**禁止重新计算**——抄错容易查，算错查不出。
- 审核智能体对照代码与 exec 输出核查，**不在脑内重算**。

**为什么有效：** 把"易幻觉的多步推理"变成"可执行、可断言（assert）、可复现的代码"。数值对不对，跑一遍就知道，不依赖模型对自己的"信心"。

---

## 对策二：可机检的通过条件 + 题干审核（治题干漏洞）

> **核心思想：题干必须声明"题目成立 ⇔ 某个能被代码检出的客观特征"，审核据此判断题目立不立得住。**

```
题干声明通过条件，例如：
  "本题成立，当且仅当：插入序列至少触发 1 次 AVL 旋转"
                    │
                    ▼
          ┌────────────────────┐
          │  题干审核智能体       │
          │  判断通过条件是否：    │
          │  ① 存在              │
          │  ② 可证伪(能检出"没满足")│
          │  ③ 覆盖考察目标       │
          └────────────────────┘
                    │
        不合格 ─────┴───── 合格
          │                │
          ▼                ▼
      回退重设题干      进入求解
```

**反例（必须拦截的坏题）：**
- 题干说"考 AVL 旋转辨析"，通过条件却只写"树保持平衡"——**零次旋转也满足**，等于没考旋转 → 拦截。
- 正确写法："至少触发 1 次旋转"——可被 exec 计数、可证伪。

**审核还查什么：** 参数是否互相矛盾、条件是否缺失/冗余、是否符合设计卡的 `should_be`/`should_not_be`。任一项不合格，**带具体路由回退**到重设题干。

---

## 对策三：K1–K5 认知雷达 —— 让难度可量化（治难度偏离）

> **核心思想：把"难度"从主观形容词，拆成五个正交的认知维度，每维 1–5 分。难度变得可测量、可对比、可检索。**

### 五个认知维度

```
                        K1 基础认知
                     (概念/公式记忆需求)
                            5
                           /|\
                            |
        K5 跨域联动 ────────┼──────── K2 单步代入
        (跨子系统联动)       │        (单次计算需求)
                            |
                           \|/
                            1
                        K3 机制推演  ←  K4 条件路由
                      (多步串行推理)   (识别陷阱/隐含前提)
```

| 维度 | 1 分(最低) | 3 分(标准) | 5 分(最高) |
|------|-----------|-----------|-----------|
| K1 基础认知 | 常识即可 | 必须记核心概念 | 纯概念辨析，无推演余地 |
| K2 单步代入 | 几乎不算 | 常规公式代入 | 整题卡这一步复杂计算 |
| K3 机制推演 | 无需推演 | 3–5 步固定流程 | 极长程，错一步全盘输 |
| K4 条件路由 | 题面即全部 | 有明确陷阱词 | 专为反直觉设计 |
| K5 跨域联动 | 单一知识点 | 两系统单向拼接 | 多系统深度耦合 |

### 难度怎么从真题里"抽取"出来

```
题库真题(2000+)
    │
    │  ① 单题打分：每道真题按五维 1–5 分标注
    ▼
单题 K 雷达，如 {K1:4, K2:2, K3:4, K4:3, K5:1}
    │
    │  ② 题位聚合：按题位(如选择题Q1)统计多年真题
    ▼
题位难度锚点(经验卡)：
    K1 众数=3 [2,4]   K2 众数=2 [1,3]  ...
    │
    │  ③ 出题时按 K 值门控 + MAE 排序检索最接近的往年题作参考
    ▼
出题锚定往年同类题的认知负荷分布，不凭空生成
```

**为什么有效：** 出题不再是"我觉得这是中等难度"，而是"目标 K 雷达 = {K3:4 主导}，从题库里检索认知负荷最接近的往年题作锚点"。难度和考点都有**客观依据**，漂移被有效约束。

## 整体架构草图：交互层 + 出题流水线

```
┌─────────────────────────────────────────────────────────────┐
│                      交互层 (需求澄清)                       │
│                                                             │
│   教师模糊需求 ──▶ 两层澄清 ──▶ 最小需求文档                │
│   "出几道树的题"    ①粗知识点    (paper_request.yaml /       │
│                      ②考察方式     slot_blueprint.yaml)      │
│                                                             │
│   规划智能体自主排布整卷，工具(KG检索/grep题库)只辅助        │
└───────────────────────────┬─────────────────────────────────┘
                            │ 交接文档
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                    出题流水线 (五层)                          │
│                                                             │
│  L1 规划 ─▶ L2 出题 ─▶ L3 审核 ─▶ L4 求解 ─▶ L5 终审         │
│              │         │        │          │                 │
│              │    不合格回退   算错回退    带路由修正          │
│              ▼         │        │          ▼                 │
│         (不写答案!) ───┘        │       final.md             │
│                                 │                            │
│         ┌───────────────────────┘                            │
│         ▼                                                    │
│   gen.py(exec算真相) ──▶ solution.md(忠实抄写)              │
└─────────────────────────────────────────────────────────────┘
```

**两条贯穿全局的纪律：**
1. **答案由独立的求解智能体产出**，出题时绝不写答案（防止"先射箭后画靶"）。
2. **审核是带路由的修正循环**，不是简单的"通过/不通过"——按问题类型回退到正确的修复点，做最小修改而非整题重做。

## 每个智能体的职责

### 交互层（需求澄清）

| 智能体 | 职责 | 不做什么 |
|--------|------|---------|
| **规划智能体 (interact)** | 把教师模糊需求通过两层澄清收敛成最小需求文档；自主排布整卷知识点、难度、考法 | 不出题，不写答案；不替教师勾选（决策权归教师） |

### 出题层（题目生产）

| 智能体 | 职责 | 对应挑战 |
|--------|------|---------|
| **规划 (design_card)** | 写设计卡：考什么、为什么这么考、K 雷达目标、`should_be`/`should_not_be`、设问骨架（复用往年题） | 难度偏离（K 雷达锚定） |
| **出题 (design_direct)** | 读设计卡，套骨架写题干 + 设问 + 经验值参数。**不写答案** | 内容偏离（按设计卡约束考点） |
| **写代码 (write_gen)** | 读题干写 `gen.py` 并 exec 验证；选择题额外派生干扰项。**用代码算真相** | 事实性错误 |
| **写文档 (write_solution)** | 读 `gen.py` + exec 输出，整理成 `solution.md`。**忠实抄写，不重算** | 事实性错误 |
| **双审核 (dual_review)** | 阶段A审代码建模 + 断言；阶段B审文档忠实。**对照判据判断，不重解题** | 题干漏洞 + 事实性错误 |
| **终审 (final_review)** | 求解正确性、答案唯一性、自洽性；带路由修正（措辞/题目/求解三类回退） | 综合质量 |

### 智能体协作的关键约束

```
design_card (设计卡) = 整道题的"宪法"
   ├─ 下游所有环节只"实现"，不"推翻"
   ├─ should_be / should_not_be / K目标 / 难度  不得修改
   └─ 审核据此对照，是质量的基准线

审核路由（最小回退）：
   题干漏洞      ──▶ 回 出题 重设题干
   代码建模错    ──▶ 回 写代码 修正 gen.py
   文档抄写错    ──▶ 回 写文档 修正 solution
   措辞/格式问题 ──▶ 就地修正
```

## 组卷场景：常驻团队 + 团队黑板

出一张完整的卷子时，智能体组成**常驻团队**，跨题复用：

```
┌─────────────── TeamPipeline (一张试卷一个实例) ───────────────┐
│                                                              │
│   design_direct ─▶ write_gen ─▶ write_solution ─▶ dual_review│
│        │                                          │          │
│        │  注入黑板(已出题记录)                      │          │
│        │◀─────────────────────────────────────────┘          │
│        │  每题完成追加摘要                                        │
│        ▼  软性避开重复考点                                      │
│   ┌──────────────┐                                           │
│   │ 团队黑板       │  paper_state.md (轻量摘要)                 │
│   │ 题位│考点│难度│  单题工作记忆每题清空防膨胀                  │
│   └──────────────┘                                           │
└──────────────────────────────────────────────────────────────┘
```

**为什么这样设计：**
- **跨题一致性**：黑板让团队"记住"已经出过什么，避免一张卷子考点/考法重复。
- **成本控制**：智能体实例不重新拉起；单题工作记忆每题清空，黑板只存轻量摘要。

## 题型自适应（一套系统，多种题型）

| 题型 | 特殊处理 |
|------|---------|
| **选择题** | 代码算出正确值后派生 3 个干扰项（真实计算错误的产物）；额外审选项互异、正确值唯一 |
| **综合题** | 共享题干 + 子问链（基础 → 进阶 → 区分度），子问串行依赖 |
| **概念题** | 批量出题，一次调用覆盖多个考点；审核用题型自适应 rubric |
| **算法设计题** | 定义类型 + 描述思想 + 写代码（关键处注释）三段式 |

---

## 一句话总结

> **我们用 K1–K5 认知雷达把"难度"变成可量化的客观量（治难度偏离），
> 用 Code as Truth 把"正确性"交给可执行代码兜底（治事实性错误），
> 用可机检的通过条件 + 带路由的审核循环守住题干质量（治题干漏洞）。**

从"会解题"走向"会出题、会诊断、会自适应"——为每个学生生成恰好卡在其能力边界上的训练题。
