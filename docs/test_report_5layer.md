- **选项架构**: 四个选项为四个不同的数值结果。通常包含一个正确答案，以及三个基于常见计算错误（如公式记反、单位未换算、权重遗漏、符号扩展错误）得出的干扰值。

  - **单位换算错误**: 混淆 $GHz/MHz/kHz$ 与 $s/ms/\mu s/ns$ 的数量级关系（如 $10^9$ vs $10^{-9}$）。

# 2009年 Q12 — 数据表示与运算（补码、符号扩展、溢出）

**知识点**: 补码表示, 符号扩展, 定点数加法运算 | **雷达形状**: K4陷阱型

**K值**:
  - K1=4: 需精准辨析“符号扩展”与“零扩展”的区别，以及补码负数在低位到高位的转换规则。若概念模糊（如认为补1是随意填充或混淆原码补码定义），无法入题。不是5分，因为通过计算可以验证答案，非纯记忆。
  - K2=3: 需进行进制转换（十进制转十六进制补码）和定点数加法。涉及非2的幂次（127, -9）和负数补码计算，属于标准难度。不是4分，因为计算量不大，不涉及复杂多级换算。
  - K3=2: 逻辑路径短：确定x补码 -> 确定y补码 -> y符号扩展至32位 -> 相加 -> 取结果。仅需2-3步串行推导。不是3分，因为流程固定且无分支。
  - K4=4: 核心陷阱在于C语言中的**隐式类型提升**（Integer Promotion）。学生极易忽略 `short` 转为 `int` 时需要进行**符号扩展**（Sign Extension），而是直接截断或错误填充。这是典型的“隐含前提”陷阱
  - K5=2: 主要涉及数据表示（CO-2）和基础运算，虽提及C语言（软件层），但本质是硬件级的补码运算，无跨系统深度耦合。

**题干**: 一个C语言程序在一台32位机器上运行。程序中定义了三个变量x、y和z,其中x和z为int型，y为short 型。当x=127,y=-9时，执行赋值语句z=x+y后，x、y和z的值分别是
A.x=0000007FH,y=FFF9H,z=00000076H
B. X= 0000007FH, y= FFF9H, Z=FFFF0076H 
C. X= 0000007FH, y= FFF7H, Z= FFFF0076H 
D.x=0000007FH,y=FFF7H,z=00000076H

**选项分析**:
- **选项A**: [干扰] — **针对错误认知**：忽略类型转换，直接进行位运算或错误填充。例如，学生可能直接将8位/16位的y补码与32位x相加，未做符号扩展，或者在扩展时高位补0（当作无符号数处理）。这类学生通常对“有符号数高位补符号位”规则记忆不牢。
- **选项B**: [干扰] — **针对错误认知**：补码计算错误或符号扩展错误。例如，计算出y的补码错误（如将-9算成其他值），或者在符号扩展时出错。或者是计算x+y时发生溢出判断错误（本题未溢出，但若误判溢出会选错）。这类学生具备基本概念但计算粗心或细节掌握不准。
- **选项C**: [干扰] — **针对错误认知**：进制转换错误。例如，在将十进制转换为十六进制补码时出错，或者混淆了原码、反码、补码的转换关系。这类学生基础薄弱，对机器数表示不熟练。
- **选项D**: [正确] — **正确路径**：x=127 (0x0000007F), y=-9 (16位补码0xFFF7 -> 32位符号扩展0xFFFFFFF7)。相加：0x0000007F + 0xFFFFFFF7 = 0xFFFFFFD6。D6对应十进制 -42。选项给出正确的十六进制或十进制结果。

**干扰策略**: 渐进陷阱

核心陷阱: 符号扩展（Sign Extension）。在C语言中，`short` 类型的 `y` 参与 `int` 类型的运算时，会自动提升为 `int` 类型。对于有符号负数，高位必须补 `1` 以保持数值不变，而非补 `0` 或直接拼接低位。

# 2012年 Q12 — CPU执行时间与系统时间计算

**知识点**: CPU执行时间, 系统时间构成, 阿姆达尔定律基础 | **雷达形状**: K4陷阱型（兼K2计算）

**K值**:
  - K1=3: 必须准确记忆“CPU时间”与“I/O时间”在计算机系统性能指标中的定义及构成关系，以及“速度”与“时间”的反比关系概念。若仅凭常识（如认为速度提高时间就减半）则无法入题，需调用计组中关于系统时间组成的核心概念。
  - K2=3: 需代入常规公式计算。虽然数字简单（100, 90, 10），但核心在于非线性的比例换算（$T_{new} = T_{old} / (1+50\%)$），而非简单的加减或整数倍乘除，涉及小数或分数的处理，符合“标准”级计算需求。
  - K3=1: 无需推演流程。题目给定初始状态和变化条件，直接通过单一公式即可得出结果，不存在多步串行推演或状态更新过程。
  - K4=3: 存在明确的陷阱词“速度提高50%”。若不触发对“速度与时间成反比”这一机制的理解，直接将其线性映射为“时间减少50%”或“减少固定值”，就会用错逻辑/公式。这是典型的语言表述陷阱。
  - K5=1: 单一知识点内部解决。虽然涉及CPU和I/O两个部件，但在本题模型中，两者时间是串行叠加关系（$T_{total} = T_{cpu} + T_{io}$），不涉及跨系统的复杂状态传递或耦合逻辑，属于简单的系统概述层级。

**题干**: 假定基准程序A在某计算机上的运行时间为100秒，其中90秒为CPU时间，其余为I/O时间。若CPU速度提高50%，I/O速度不变，则运行基准程序A所耗费的时间是
A.55s
B.60s
C.65s
D.70s

**选项分析**:
- **选项A**: [干扰] — 对应原题选项B（55秒）。针对认知错误：将“速度提高50%”误解为“时间减少50%”。计算逻辑：$90 \times (1 - 0.5) + 10 = 45 + 10 = 55$。这类学生通常对速度与时间的反比关系理解不深，或受日常语言直觉误导。
- **选项B**: [正确] — 对应原题正确答案（70秒）。正确逻辑：CPU速度提高50%，即新速度是原速度的1.5倍，故新CPU时间为 $90 / 1.5 = 60$ 秒。总时间 = $60 + 10 = 70$ 秒。
- **选项C**: [干扰] — 对应原题选项C（80秒）。针对认知错误：计算错误或逻辑混乱。例如可能误以为CPU时间减少1/3但算错，或者混淆了提速前后的比例关系。也有可能是将I/O时间也误认为参与提速后的某种错误加权。
- **选项D**: [干扰] — 对应原题选项D（85秒）。针对认知错误：另一种计算错误。例如可能误算 $90 / 1.5 \approx 60$ 但加错了I/O时间，或者误以为速度提高50%意味着时间变为 $90 / (1+0.5)^{-1}$ 等混乱逻辑。*注：原题选项D通常为其他数值，此处根据常见错误分布分析，85秒可能对应 $90 - (90 \times 50\% / 2)$ 等奇怪逻辑，或单纯计算失误*。

**干扰策略**: 并行陷阱（各干扰项独立）

核心陷阱: 语言表述陷阱——混淆“速度提升比例”与“时间缩短比例”。

  - K2=2: 仅需一步简单的乘法代入（20 * 0.7 * 1.2），数字友好，无复杂单位换算或非2的幂次计算。
  - K3=1: 无需多步串行推演，直接套用公式即可得出结果，路径唯一且极简。
  - K4=2: 存在常规注意点（即需要同时考虑指令数减少和CPI增加两个变量的变化），408考生通常不会遗漏，无深层隐含前提或反直觉设计。
  - K5=1: 单一知识点内部解决，仅涉及CPU性能指标体系，不涉及存储、IO等其他系统的联动。

**题干**: 程序P在机器M上的执行时间是20秒，编译优化后，P执行的指令数减少到原来的70%,而CPI增加到原来的1.2倍，则P在M上的执行时间是。
A.8.4秒
B.11.7秒
C.14秒
D.16.8秒

**选项分析**:
- **选项A**: 干扰 — 计算错误或比例用错（如误以为执行时间随指令数线性减少而忽略CPI影响，或计算失误）。针对计算粗心或对公式结构模糊的学生。

# 2009年 Q12 — 数据表示与运算（补码、符号扩展、溢出）

**知识点**: 补码表示, 符号扩展, 定点数加法运算 | **雷达形状**: K4陷阱型

**K值**:

A.x=0000007FH,y=FFF9H,z=00000076H
B. X= 0000007FH, y= FFF9H, Z=FFFF0076H 
C. X= 0000007FH, y= FFF7H, Z= FFFF0076H 
D.x=0000007FH,y=FFF7H,z=00000076H

**选项分析**:
- **选项A**: [干扰] — **针对错误认知**：忽略类型转换，直接进行位运算或错误填充。例如，学生可能直接将8位/16位的y补码与32位x相加，未做符号扩展，或者在扩展时高位补0（当作无符号数处理）。这类学生通常对“有符号数高位补符号位”规则记忆不牢。

- **选项C**: [干扰] — **针对错误认知**：进制转换错误。例如，在将十进制转换为十六进制补码时出错，或者混淆了原码、反码、补码的转换关系。这类学生基础薄弱，对机器数表示不熟练。

# 2012年 Q12 — CPU执行时间与系统时间计算

**知识点**: CPU执行时间, 系统时间构成, 阿姆达尔定律基础 | **雷达形状**: K4陷阱型（兼K2计算）

**K值**:
  - K1=3: 必须准确记忆“CPU时间”与“I/O时间”在计算机系统性能指标中的定义及构成关系，以及“速度”与“时间”的反比关系概念。若仅凭常识（如认为速度提高时间就减半）则无法入题，需调用计组中关于系统时间组成的核心概念。
  - K2=3: 需代入常规公式计算。虽然数字简单（100, 90, 10），但核心在于非线性的比例换算（$T_{new} = T_{old} / (1+50\%)$），而非简单的加减或整数倍乘除，涉及小数或分数的处理，符合“标准”级计算需求。
  - K3=1: 无需推演流程。题目给定初始状态和变化条件，直接通过单一公式即可得出结果，不存在多步串行推演或状态更新过程。
  - K4=3: 存在明确的陷阱词“速度提高50%”。若不触发对“速度与时间成反比”这一机制的理解，直接将其线性映射为“时间减少50%”或“减少固定值”，就会用错逻辑/公式。这是典型的语言表述陷阱。
  - K5=1: 单一知识点内部解决。虽然涉及CPU和I/O两个部件，但在本题模型中，两者时间是串行叠加关系（$T_{total} = T_{cpu} + T_{io}$），不涉及跨系统的复杂状态传递或耦合逻辑，属于简单的系统概述层级。

**题干**: 假定基准程序A在某计算机上的运行时间为100秒，其中90秒为CPU时间，其余为I/O时间。若CPU速度提高50%，I/O速度不变，则运行基准程序A所耗费的时间是
A.55s
B.60s
C.65s
D.70s

**选项分析**:
- **选项A**: [干扰] — 对应原题选项B（55秒）。针对认知错误：将“速度提高50%”误解为“时间减少50%”。计算逻辑：$90 \times (1 - 0.5) + 10 = 45 + 10 = 55$。这类学生通常对速度与时间的反比关系理解不深，或受日常语言直觉误导。
- **选项B**: [正确] — 对应原题正确答案（70秒）。正确逻辑：CPU速度提高50%，即新速度是原速度的1.5倍，故新CPU时间为 $90 / 1.5 = 60$ 秒。总时间 = $60 + 10 = 70$ 秒。
- **选项C**: [干扰] — 对应原题选项C（80秒）。针对认知错误：计算错误或逻辑混乱。例如可能误以为CPU时间减少1/3但算错，或者混淆了提速前后的比例关系。也有可能是将I/O时间也误认为参与提速后的某种错误加权。
- **选项D**: [干扰] — 对应原题选项D（85秒）。针对认知错误：另一种计算错误。例如可能误算 $90 / 1.5 \approx 60$ 但加错了I/O时间，或者误以为速度提高50%意味着时间变为 $90 / (1+0.5)^{-1}$ 等混乱逻辑。*注：原题选项D通常为其他数值，此处根据常见错误分布分析，85秒可能对应 $90 - (90 \times 50\% / 2)$ 等奇怪逻辑，或单纯计算失误*。

**干扰策略**: 并行陷阱（各干扰项独立）

核心陷阱: 语言表述陷阱——混淆“速度提升比例”与“时间缩短比例”。

  - **选项 D (200 μs)**: 针对“CPI 直接相加”的错误认知。学生可能完全误解 CPI 概念，将两类 CPI 直接相加 $1+4=5$，计算得 $64000 \times 5 / 1.6 \times 10^9 = 200 \mu s$。
- **代码验证结果摘要**: 
  - 加权平均 CPI 计算正确 (1.75)。
  - 正确执行时间计算为 70.0 μs，结果为整数。
  - 干扰项 B (算术平均) 对应 100.0 μs。
  - 干扰项 D (CPI 相加) 对应 200.0 μs。
  - 所有参数封闭，无逻辑矛盾，整除性良好。
- **与契约 K 值的对齐说明**: 
  - K1=3: 需准确记忆 CPU 执行时间公式和加权平均概念。
  - K2=3: 涉及非 2 的幂次主频和多级单位换算 (GHz → μs)。

### 发现的问题

#### BUG-1 [HIGH]: Review Agent 输出缺少 `## status` 段

**现象**: Review Agent 两次写入 review.md，均使用表格报告格式（`# Q12 题目审核报告` + `## Step 1-5` + `## 最终判定`），而非要求的 `## status` 格式。

**影响**: `get_doc_status()` 返回空字符串，不匹配 "pass"，导致不必要的 Question 重出题循环。本应 1 轮 pass 的流程被迫走了 3 轮，增加 2 分钟耗时和 token 消耗。

**根因**: Qwen 模型未严格遵循 agent 提示语中指定的输出格式。Review Agent 的 `review_skill.md` 使用了表格化审核清单，Qwen 将其理解为"按检查清单逐项判断"而非"按指定格式输出"。

**修复建议**:
1. 在 review_skill.md 开头增加**格式模板**（示例输出），而不仅仅是列出审核维度
2. 在 scheduler 的 retry 逻辑中，如果 status 为空，尝试从内容中提取 pass/needs_fix 关键词（如 `**审核结论**: ✅ **pass**`）

#### BUG-2 [HIGH]: Final Review Agent 同样缺少 `## status` 段

**现象**: Final Review 写入 `## 审核结论\npass` 和 `## 路由判定\npass`，而非 `## status\npass`。

**影响**: Pipeline 结果中 `review_status` 为空，下游无法知道终审结果。但由于是最终迭代，流程仍继续执行并输出 final.md。

**根因**: 同 BUG-1，Qwen 未使用指定的 `## status` 段格式。

**修复建议**:
1. 在 final_review_skill.md 中增加格式模板
2. 增加模糊匹配 fallback：如果 `## status` 缺失，搜索 `pass|expression_fix|question_error|solution_error` 关键词

#### OBS-1 [MEDIUM]: Question Agent 第1次调用使用 exec_python 后未调用 write_file

**现象**: 第1次调用时，Question Agent 先用 exec_python 验证参数（正确行为），但返回 `finish_reason=tool_calls` 后 scheduler 判定 "tool_calls did not write question.md"。第2次调用才成功写入。

**影响**: 增加 1 次额外 LLM 调用（约 15s）。但此行为符合设计：multi_turn 允许多步，scheduler 正确检测到还没写文件就继续。

**评估**: 这是预期行为，不是 bug。Agent 先验证参数再写文件是正确的工作流。

#### OBS-2 [LOW]: Solve Agent 未生成 solve.py

**现象**: 尽管这是一道数值计算题（CPU 执行时间公式），Solve Agent 只用了 exec_python 做中间验证，没有将代码写入 solve.py 文件。

**影响**: 无 solve_output.txt，但 solution.md 包含完整求解过程和正确答案。Pipeline 标记 `code_skipped=True`。

**评估**: Solve Agent 理解了"概念/数值题"判断，选择直接推理+exec_python 验证。代码未持久化为 solve.py，但求解正确。可以接受，但可考虑在 skill 中强调"数值题应保留 solve.py"。
