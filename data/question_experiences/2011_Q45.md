# 2011 Q45 — 生产者-消费者模型变体与多信号量同步

## 基本信息
- **年份**: 2011  **题位**: Q45  **题型**: 综合题
- **知识点**: 同步问题设计, 操作系统>同步问题设计
- **题位域**: 待标注  **科目**: 操作系统

## 题干原文
某银行提供 1 个服务窗口和 10 个顾客等待座位。顾客到达银行时，若有空座位，则到取号机领取一个号，等待叫号。取号机每次仅允许一位顾客使用。当营业员空闲时，通过叫号选取一位顾客，并为其服务。顾客和营业员的活动过程描述如下：
cobegin
{
 process 顾客 i 
 {
 从取号机获得一个号码;
 等待叫号;
 获得服务;
 }

 process 营业员
 {
 while (TRUE) {
 叫号;
 为顾客服务;
 }
 }
}coend
请添加必要的信号量和 P、V（或
wait()
、signal()
）操作实现上述过程的互斥和同步。要求写出完整的过程，说明信号量的含义并赋初值。

## K1-K5 评分与解析
- **K1 = 3**: 评分理由。需要掌握信号量机制、P/V操作语义、互斥与同步的基本概念。不是4分因为不需要辨析多个易混的高级同步原语（如管程、自旋锁等），属于操作系统核心基础概念的标准应用。
- **K2 = 1**: 评分理由。本题不涉及数值计算，无需执行复杂的算术或逻辑运算，仅涉及信号量值的初始化和P/V操作的逻辑顺序。
- **K3 = 4**: 评分理由。解题过程需要多步串行推演：首先识别资源（座位、取号机、服务窗口），其次确定同步关系（顾客-座位、顾客-取号机、顾客-营业员），最后确定P/V操作的严格顺序。步骤超过5步且需保持中间状态（如先P座位再P取号机，避免死锁），逻辑链条较长。
- **K4 = 4**: 评分理由。存在隐含前提和潜在陷阱。1. 必须意识到“取号机”是互斥资源，而不仅仅是同步点；2. 必须处理“座位”这一有限缓冲区资源；3. 最关键的是P操作的顺序：若先P(mutex)再P(empty)，当座位满时，持有mutex的顾客会阻塞，导致其他顾客无法进入等待区，造成死锁或资源浪费。识别这一隐含的死锁风险并正确排序P操作是高分关键。
- **K5 = 4**: 评分理由。需要在“顾客进程”和“营业员进程”两个子系统间传递状态。顾客通过V(full)通知营业员有顾客，营业员通过V(service)通知顾客可以服务。同时，顾客内部还需协调“座位”和“取号机”两个资源的状态。这种多进程、多资源的状态耦合属于深度联动。
- **雷达形状**: 偏向右侧（K3, K4, K5较高），左侧（K1, K2）较低。呈现典型的“逻辑推演与系统设计”型特征，而非计算或记忆型。

## 考察模式
- **模式**: 综合型
- **理由**: 本题结合了互斥（取号机）和同步（座位缓冲、服务通知）两种机制，要求考生将经典的“生产者-消费者”模型进行变体应用（生产者=顾客，消费者=营业员，缓冲区=座位，额外互斥=取号机）。它不是单纯的算法设计，也不是简单的概念辨析，而是要求构建完整的并发控制逻辑。

## 解题思路分析
- **核心思路**: 将问题分解为三个独立的同步/互斥问题，并合并到进程代码中。
    1. **互斥问题**：取号机是临界资源，需互斥信号量 `mutex`。
    2. **同步问题1（座位缓冲）**：顾客需要空座位才能进入，营业员服务后释放座位（隐含在顾客离开或新顾客进入逻辑中，但本题模型中座位是顾客等待的资源，通常视为生产者-消费者中的缓冲区）。这里更准确的理解是：`empty` 表示空座位数，`full` 表示已占座位数（即等待服务的顾客数）。
    3. **同步问题2（服务通知）**：顾客取号后等待叫号，营业员叫号后通知顾客。需信号量 `service`。
- **关键步骤**:
    1. **定义信号量**：
       - `mutex = 1`：互斥使用取号机。
       - `empty = 10`：初始空座位数。
       - `full = 0`：初始等待顾客数（已占座位）。
       - `service = 0`：初始无顾客等待服务。
    2. **顾客进程逻辑**：
       - 先 `P(empty)`：申请座位。若座位满，阻塞。
       - 再 `P(mutex)`：申请取号机。
       - 取号。
       - `V(mutex)`：释放取号机。
       - `V(full)`：通知营业员有顾客等待（座位被占用，顾客就绪）。
       - `P(service)`：等待营业员叫号。
       - 接受服务。
       - `V(empty)`：服务结束，释放座位（注意：原题描述中顾客获得服务后离开，座位变空，供下一位顾客使用。虽然题干未明确写“离开”，但“10个等待座位”暗示座位是循环使用的资源，或者更严谨地说，顾客离开后座位才空。但在标准解法中，通常认为顾客服务结束后释放座位资源，或者在取号前申请座位，服务后释放。*修正*：根据经典解法，顾客取号后进入等待队列，服务结束后离开，座位变为空。因此顾客进程末尾应有 `V(empty)`。但观察题干“顾客到达...若有空座位...取号...等待...服务”，通常模型中，座位是等待区的资源。顾客服务完后离开，座位空出。所以顾客进程最后应 `V(empty)`。然而，很多标准答案为了简化，可能只关注进入时的同步。让我们仔细看参考答案的逻辑：参考答案中顾客进程最后是 `接受服务`，没有显式写 `V(empty)`，但营业员进程也没有 `V(empty)`。这通常意味着题目隐含顾客服务后离开，座位自动释放，或者题目模型中座位仅用于限制并发进入的顾客数。*更正*：在经典的银行叫号模型中，座位是缓冲区。顾客进入缓冲区（P empty），离开缓冲区（V empty）。如果顾客服务后不释放座位，座位会耗尽。因此，完整的顾客进程应在服务后 `V(empty)`。*再次检查参考答案*：参考答案中顾客进程最后是 `接受服务`，营业员进程是 `叫号; 服务;`。如果严格按照“10个座位”限制，顾客服务完后必须释放座位。但有些简化模型认为座位仅用于“等待”，服务时不在座位上。无论哪种，`empty` 的 V 操作必须在顾客离开等待区后。通常放在服务结束后。
    3. **营业员进程逻辑**：
       - `P(full)`：等待有顾客。
       - 叫号。
       - `V(service)`：通知特定顾客（或广播，但在信号量模型中通常简化为唤醒一个等待者，或者假设叫号机制能精确唤醒。在信号量解法中，`V(service)` 会唤醒一个 `P(service)` 的顾客）。
       - 服务。
- **易错点**:
    1. **P操作顺序错误**：在顾客进程中，若先 `P(mutex)` 后 `P(empty)`，当座位满时，持有 mutex 的顾客阻塞，其他顾客无法进入，导致死锁或系统停滞。必须遵循“先申请资源（座位），再申请互斥（取号机）”或确保不会因持有互斥锁而等待资源的原则。
    2. **信号量含义混淆**：混淆 `full` 和 `service`。`full` 是顾客通知营业员“我来了”，`service` 是营业员通知顾客“轮到你了”。
    3. **遗漏互斥**：忘记对取号机进行互斥保护。
    4. **遗漏座位释放**：忘记在服务结束后 `V(empty)`，导致座位资源泄漏（虽然本题题干未明确循环，但作为资源管理题，通常需要考虑）。*注：根据2011年真题的标准答案，顾客进程最后确实没有显式写出 V(empty)，可能是因为题目侧重于“进入等待区”的同步，或者隐含在服务过程中座位已释放。但在严谨的同步设计中，应包含。此处以标准答案逻辑为主，通常标准答案中顾客进程为：P(empty), P(mutex), 取号, V(mutex), V(full), P(service), 服务。*

## 核心陷阱
- **核心陷阱**: **P操作的顺序导致的死锁风险**。
  考生极易写出 `P(mutex); P(empty);` 的顺序。
  **分析**：假设座位已满（empty=0），顾客A执行 `P(mutex)` 成功，接着执行 `P(empty)` 阻塞。此时 mutex=0。顾客B到达，执行 `P(mutex)` 阻塞。所有后续顾客都阻塞在 mutex 上，无法执行 `P(empty)` 来检查座位，也无法释放 mutex。虽然此时没有新的座位释放（因为没人能进入），但如果系统中有其他机制释放座位，这里就会死锁。更严重的是，如果 `empty` 初始值较小，这种顺序会导致系统吞吐量急剧下降甚至死锁。正确的顺序是 `P(empty); P(mutex);`，确保只有在有座位的情况下才去竞争取号机，或者即使竞争失败，也不会阻塞其他顾客检查座位。

## 考察能力
本题核心考察考生将现实场景抽象为并发模型的能力，以及在多资源、多进程环境下正确设计信号量以解决互斥和同步问题，特别是避免死锁的逻辑思维能力。
