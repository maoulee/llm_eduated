# 模拟题 Q综合题 — 多进程同步与资源匹配

## 基本信息
- **来源**: 模拟题  **题型**: 综合题
- **科目**: 操作系统
- **知识点**: OS-2 > 2.3 进程同步 > 同步与互斥基本概念, OS-2 > 2.3 进程同步 > P、V操作
- **难度**: 待评估

## 题干原文
（8 分）在一间酒吧里有 3 个音乐爱好者队列，第 1 队的音乐爱好者只有随身听，第 2 队只有音乐磁带，第 3 队只有电池。而要听音乐就必须随身听、音乐磁带和电池这 3 种物品俱全。酒吧老板一次出售这 3 种物品中的任意两种。当一名音乐爱好者得到这 3 种物品并听完一首乐曲后，酒吧老板才能再一次出售这 3 种物品中的任意两种。于是第 2 名音乐爱好者得到这 3 种物品，并开始听乐曲。全部买卖就这样进行下去。试用 P、V 操作正确解决这一买卖。

## K1-K5 评分与解析
- **K1 = 3**: 评分理由。需要掌握P/V操作的基本语义（P减1，V加1，阻塞与唤醒机制）以及信号量在同步与互斥中的基本应用。属于标准的基础概念记忆，不涉及复杂公式或深层理论辨析。
- **K2 = 1**: 评分理由。本题不涉及数值计算，无需进行幂次运算或单位换算，属于纯逻辑设计题。
- **K3 = 4**: 评分理由。推演步骤较多且需维护中间状态。需要理清“老板卖货 -> 顾客匹配 -> 顾客付费/拿货 -> 顾客听歌 -> 老板再卖货”这一完整闭环。特别是“老板卖任意两种”与“顾客缺一种”之间的逻辑映射，以及“听歌结束”作为下一次循环触发条件的状态流转，步骤超过5步且需记忆多个信号量的状态变化。
- **K4 = 4**: 评分理由。存在隐含前提和逻辑陷阱。题面未明确说明“付费”环节，但参考答案引入了`payment`和`goods`信号量来模拟交易过程，这是典型的隐含业务逻辑。此外，需识别“老板卖出的两种物品”必须恰好是“某类顾客缺失的那两种”，否则无法完成同步，这种条件路由需要考生自行构建逻辑判断（if-else分支）。
- **K5 = 4**: 评分理由。涉及多个进程（老板、三类顾客）之间的深度状态耦合。老板的状态取决于顾客是否完成听歌（`music_over`），顾客的状态取决于老板卖出的物品类型（`buy1/2/3`），且交易过程涉及双向同步（`payment`和`goods`）。不同子系统（卖方、买方、消费方）间状态互影响，耦合度高。
- **雷达形状**: 偏向右侧的不对称形状，K3、K4、K5较高，K1中等，K2极低。呈现典型的“逻辑设计类”题目特征，重推演与联动，轻计算。

## 考察模式
- **模式**: 算法设计型
- **理由**: 题目要求考生使用P/V操作编写伪代码来解决具体的进程同步问题，属于典型的并发控制算法设计。

## 解题思路分析
- **核心思路**: 将问题分解为“资源供给”、“资源匹配”、“交易同步”和“消费同步”四个阶段。利用信号量表示特定资源的可用性，利用信号量协调买卖双方的动作顺序，利用信号量协调消费结束与下一轮供给的关系。
- **关键步骤**:
    1.  **定义信号量**:
        -   `buy1`, `buy2`, `buy3`: 分别表示老板卖出了“磁带+电池”、“随身听+电池”、“随身听+磁带”。初值为0。
        -   `payment`: 顾客付费信号，初值0。
        -   `goods`: 老板交货信号，初值0。
        -   `music_over`: 听歌结束信号，初值0。
    2.  **老板进程 (Boss)**:
        -   循环执行：
        -   等待 `music_over` (P操作)，确保上一位顾客听歌结束。
        -   随机选择两种物品出售。
        -   根据出售组合，执行对应的 `V(buy1)` 或 `V(buy2)` 或 `V(buy3)`。
        -   等待顾客付费 `P(payment)`。
        -   交货 `V(goods)`。
    3.  **顾客进程 (Customer 1/2/3)**:
        -   以Customer 1（缺磁带+电池）为例：
        -   等待对应资源 `P(buy1)`。
        -   付费 `V(payment)`。
        -   等待交货 `P(goods)`。
        -   听歌（模拟耗时）。
        -   通知老板听歌结束 `V(music_over)`。
        -   (Customer 2和3逻辑类似，分别等待 `buy2` 和 `buy3`)。
- **易错点**:
    1.  **信号量初值设置错误**: 忘记所有资源信号量初值为0，导致死锁或逻辑错误。
    2.  **同步顺序颠倒**: 例如顾客先 `V(goods)` 再 `P(payment)`，或者老板先 `V(goods)` 再 `P(payment)`，导致逻辑混乱。
    3.  **遗漏 `music_over`**: 忘记在老板再次卖货前等待顾客听歌结束，导致老板可能在顾客听歌时再次卖货，违反题意“听完一首乐曲后...才能再一次出售”。
    4.  **逻辑分支缺失**: 老板进程中未根据出售物品类型进行 `if-else` 判断，直接 `V` 所有信号量或固定 `V` 某一个，导致资源匹配错误。

## 核心陷阱
- **核心陷阱**: **隐含的交易同步环节**。题目文字描述侧重于“物品匹配”和“听歌同步”，但参考答案引入了 `payment` 和 `goods` 两个信号量来模拟“一手交钱一手交货”的过程。如果考生仅关注物品匹配和听歌结束，可能会忽略买卖动作本身的原子性或顺序性，导致模型过于简化而不符合“买卖”的完整语义。此外，老板出售物品的“任意性”需要通过代码逻辑（if-else）显式表达，而非隐式假设。

## 考察能力
本题核心考察考生将自然语言描述的复杂并发场景抽象为进程同步模型的能力，特别是多条件分支下的资源匹配与多阶段动作的顺序控制能力。
