# 练习题 Q1 — 直接映射Cache缺失率计算

## 基本信息
- **来源**: 练习题  **题型**: 选择题
- **科目**: 操作系统
- **知识点**: 计算机组成原理/存储系统
- **难度**: 待评估

## 题干原文
某 CPU 具有 32KB 直接映射高速缓存，块大小为 128 字节。假设 A 是一个 512×512 的二维数组，每个元素占用 8 字节。考虑以下代码段：
```c
for (i = 0; i < 512; i++) {
    for (j = 0; j < 512; j++) {
        x += A[i][j];
    }
}
```
假设数组按 A[0][0], A[0][1], A[0][2]……顺序存储，则高速缓存缺失次数为（ ）。
- 选项:
  A: 16384
  B: 512
  C: 2048
  D: 1024
- 正确答案: A
- 解析（参考）: 块大小与元素数量计算
块大小 = 128 字节
每块包含元素数 = 128 / 8 = 16
数组存储方式
块 0：A[0][0] 到 A[0][15]
块 1：A[0][16] 到 A[0][31] 依此类推
i=0 时的缺失分析
A[0][0] 不在高速缓存中，发生缺失
后续 15 个元素（j= 1 到 j=15）命中缓存
j 从 0 到 512 循环时，每 16 个元素发生一次缺失
i=0 时总缺失次数 = 512 / 16 = 32 次
总缺失次数计算
外层 i 循环从 0 到 512
总缺失次数 = 512 × 32 = 16384
- 知识标签: ['计算机组成原理/存储系统']
- 知识域: CO-1

## K1-K5 评分与解析
- **K1 = 3**: 评分理由。需要掌握Cache的基本概念（块大小、直接映射、缺失定义）以及二维数组在内存中的线性存储规则。属于标准的基础概念记忆，不涉及复杂概念辨析。
- **K2 = 3**: 评分理由。涉及多级换算：字节转元素个数（128/8）、元素个数转块数（512/16）、总缺失次数乘法（512*32）。虽然都是2的幂次运算，但步骤较多，容易在中间环节出错。
- **K3 = 3**: 评分理由。推演过程清晰：确定块容量 -> 确定单次遍历缺失率 -> 确定总遍历次数 -> 计算总缺失。属于3-5步的标准串行推演，逻辑链条明确。
- **K4 = 2**: 评分理由。存在常规注意点：需确认数组大小是否超过Cache容量导致冲突缺失（Conflict Miss）。本题中数组总大小 $512 \times 512 \times 8 = 2MB$，远大于32KB Cache，且为直接映射，理论上存在严重的冲突缺失风险。但题目考察的是“容量缺失+强制缺失”的基础模型，或者隐含假设了理想情况/仅考察局部性原理带来的块内命中。对于初学者，容易忽略Cache容量限制带来的冲突问题，但在此题语境下，主要陷阱在于是否理解“块内连续访问命中”，属于常规注意点。
- **K5 = 1**: 评分理由。仅涉及存储系统内部机制，未跨越CPU指令执行、中断等其他子系统，属于单系统内部计算。
- **雷达形状**: K2/K3主导的计算推理型，K4略有陷阱特征。

## 考察模式
- **模式**: 计算型
- **理由**: 题目核心在于通过给定的硬件参数（Cache大小、块大小）和软件行为（循环访问模式），进行定量的缺失次数计算。虽然涉及概念理解，但最终落脚点是数值计算。

## 选项级分析
- **选项A**: [正确] — 正确理解了块大小为128字节，每块容纳16个元素，每次访问新块产生1次缺失，每行512个元素产生32次缺失，共512行，总计 $512 \times 32 = 16384$ 次。
- **选项B**: [干扰] — 针对错误认知：认为每行只缺失1次（误以为整行都在一个块中，或误以为Cache能容纳整行）。这类学生可能忽略了块大小限制，或者混淆了“行”与“块”的概念。
- **选项C**: [干扰] — 针对错误认知：计算错误。可能是将每块元素数算错（如算成8个，则每行64次缺失，$512 \times 64 = 32768$，不对）；或者是将总元素数 $512 \times 512 = 262144$ 除以块大小128得到2048个块，误以为每个块只缺失一次且不再重复访问（忽略了循环结构，或者误以为是一次性遍历所有数据）。更可能的错误路径是：算出总共有2048个不同的Cache块被访问（$2MB / 1KB$? 不对，$2MB/128B = 16384$块）。如果学生误算总块数为2048（例如误用1KB块大小），可能会选C。或者，学生计算出每行缺失32次，但只算了16行？不太像。最可能的错误是：总元素数 $262144$，每块16元素，共 $16384$ 块。如果学生误以为每个块在整个程序运行中只缺失一次（即假设Cache足够大能容纳所有块，或者误解题意），可能会去算总块数。但总块数是16384。选项C 2048可能是 $512 \times 4$？或者 $1024 \times 2$？ 另一种可能：误以为块大小是1KB（1024字节），则每块128元素，每行4次缺失，$512 \times 4 = 2048$。这是典型的参数看错陷阱。
- **选项D**: [干扰] — 针对错误认知：误以为每行缺失1次，且只计算了外层循环次数？或者误以为块大小等于行大小？如果误以为每行512个元素刚好占满一个块（实际需4KB块，而题目是128B），则每行1次缺失，共512次（选项B）。如果误以为每行缺失2次？ 选项D 1024可能是 $512 \times 2$。如果学生误算每块容纳256元素（128字节/0.5字节? 不可能）。更可能是：误以为每行缺失2次（例如误算块大小为256字节，每块32元素，512/32=16? 不对）。 或者，学生计算出总缺失16384，然后除以16（每块元素数）？ $16384/16 = 1024$。这是典型的“多除一次”错误，混淆了“缺失次数”和“块数量”的关系，或者在计算总缺失时错误地再次除以了块内元素数。

- **干扰策略**: 参数误读（块大小看错）、概念混淆（行与块的关系）、计算步骤冗余（多除一次）。

## 核心陷阱
- **核心陷阱**: **块内局部性的量化计算**。学生容易忽略“块大小”对命中率的决定性影响，错误地假设每次访问都缺失（得 $262144$，无选项），或假设整行命中（得 $512$，选项B）。关键在于准确计算“一个Cache块能容纳多少个数组元素”，从而得出“每多少个元素发生一次缺失”。此外，需警惕Cache容量过小导致的冲突缺失（Conflict Miss），但在本题标准解法中，主要考察的是基于块大小的强制缺失（Compulsory Miss）和容量缺失（Capacity Miss）的混合，且由于是直接映射，实际上每一行的不同块会映射到Cache的不同行（如果Cache行数足够）或同一行（如果发生冲突）。
    *   *深度分析*：Cache大小32KB，块大小128B，则Cache行数（Lines）= $32KB / 128B = 256$ 行。
    *   数组一行有512个元素，占 $512 \times 8 = 4096$ 字节 = 4KB。
    *   一行包含 $4096 / 128 = 32$ 个块。
    *   这32个块在直接映射Cache中，其索引（Index）取决于地址。假设基地址对齐，这32个块的地址是连续的。
    *   如果Cache只有256行，而数组总共有 $512 \times 32 = 16384$ 个块。
    *   当访问 $A[0][0]$ 到 $A[0][511]$ 时，涉及32个块。
    *   当访问 $A[1][0]$ 时，其地址与 $A[0][0]$ 相差4KB。
    *   在直接映射中，地址的Index位由地址的中间位决定。
    *   如果 $A[0][0]$ 映射到 Cache Line $L$，那么 $A[1][0]$ 的地址增加了4KB。4KB = $2^{12}$。
    *   Cache块大小128B = $2^7$。Offset占7位。
    *   Cache行数256 = $2^8$。Index占8位。
    *   地址结构：Tag | Index (8 bits) | Offset (7 bits)。
    *   $A[0][0]$ 地址 $Addr$。Index = $(Addr >> 7) \& 0xFF$。
    *   $A[1][0]$ 地址 $Addr + 4096$。$4096 = 1000000000000_2$ (12个0)。
    *   $Addr + 4096$ 的 Index 位：$(Addr + 2^{12}) >> 7 = (Addr >> 7) + 2^5 = (Addr >> 7) + 32$。
    *   所以 $A[1][0]$ 映射到 Cache Line $(L + 32) \& 0xFF$。
    *   这意味着 $A[0]$ 行的块和 $A[1]$ 行的块**不会**直接冲突（除非 $L+32$ 溢出256，即 $L \ge 224$）。
    *   即使发生冲突，题目问的是“缺失次数”。在直接映射中，如果发生冲突，旧数据被踢出，新数据缺失。
    *   由于访问模式是顺序的，且每行内部是顺序访问，每行内部的32个块会依次加载。
    *   关键在于：当处理 $A[1]$ 行时，$A[0]$ 行的数据是否还在Cache中？
    *   $A[0]$ 行的32个块占据 Cache Line $L, L+1, ..., L+31$。
    *   $A[1]$ 行的32个块占据 Cache Line $L+32, ..., L+63$。
    *   只要 $L+63 < 256$，就没有冲突。
    *   但是，当 $i$ 增大时，映射的Cache Line会循环。
    *   然而，无论是否发生冲突，**每次访问一个新的Cache块（即每16个元素），都会导致一次缺失**（因为之前的块要么被踢出，要么本来就不在，或者即使还在，直接映射的特性决定了如果新块映射到同一位置，旧块被踢出，新块缺失；如果映射到不同位置，新块缺失）。
    *   实际上，对于直接映射Cache，只要访问的块地址不同，且该块当前不在Cache中（无论是冷启动还是被踢出），就是缺失。
    *   在顺序访问中，每16个元素对应一个新块。这个新块在访问它之前，肯定不在Cache中（因为它是第一次被访问，或者之前的同映射位置块已被覆盖）。
    *   因此，**每16个元素必然产生1次缺失**。
    *   总元素数 $512 \times 512$。
    *   总缺失 = 总元素数 / 每块元素数 = $262144 / 16 = 16384$。
