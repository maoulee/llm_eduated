# 2024 Q38 — TCP连接全生命周期时序计算

## 基本信息
- **年份**: 2024  **题位**: Q38  **题型**: 选择题
- **知识点**: CN-5 > TCP协议 > TCP连接管理, CN-5 > TCP协议 > TCP三次握手, CN-5 > TCP协议 > TCP四次挥手
- **题位域**: 待标注  **科目**: 计算机网络

## 题干原文
假设主机 H 通过 TCP 向服务器发送长度为 3000B 的报文，往返时间 RTT=10ms，最长报文段寿命
MSL=30s，最大报文段长度 MSS=1000B，忽略 TCP 段的传输时廷，报文传输结束后 H 首先请求断开连接，
则从 H 请求建立 TCP 连接时刻起，到 H 进入 CLOSED 状态为止，所需时间至少是（ ）
TCP三次握手
TCP四次挥手

A. 30.03s
B. 30.04s
C. 60.03s
D. 60.04s

## K1-K5 评分与解析
- **K1 = 4**: 评分理由。需要记忆并准确调用多个核心概念：TCP三次握手、四次挥手的具体步骤、MSS对分片的影响、MSL（最大报文段寿命）在TIME_WAIT状态中的作用、以及“忽略传输时延”这一理想化条件的含义。若对MSL与TIME_WAIT的关系记忆模糊，极易出错。
- **K2 = 3**: 评分理由。涉及简单的加法运算（RTT累加）和除法运算（3000/1000），计算本身不复杂，但需要将不同阶段的时间单位（ms和s）统一，且需识别出数据传输阶段并非简单的1个RTT，而是受限于MSS和滑动窗口机制（题目隐含慢启动或至少分片发送的逻辑，虽然题目未明确提及拥塞控制，但3000B数据分3个MSS发送，通常视为连续发送或极短时间间隔，但在考研语境下，往往考察的是“发送完所有数据”这一动作完成的时间点，或者更严谨地，考察的是最后一个ACK到达的时间。*修正思考*：题目问的是“从建立连接到H进入CLOSED”。H进入CLOSED是在收到最后一个ACK之后。关键在于数据传输耗时。3000B数据，MSS=1000B，需3个报文段。忽略传输时延，发送方发出3个报文段几乎瞬间完成（或视为0时延）。接收方收到第3个报文段并回复ACK。这个ACK回到发送方需要0.5 RTT。所以数据传输阶段主要耗时是最后一个ACK的往返？不，题目说“报文传输结束后H首先请求断开”。这意味着H发完数据后，紧接着发FIN。通常认为数据发送和FIN发送之间没有额外等待，或者FIN可以捎带在最后一个数据段中（如果应用层数据发完）。但题目说“报文传输结束后...请求断开”，暗示数据发完，连接处于ESTABLISHED，然后H发FIN。
    *重新审视计算逻辑*：
    1. 三次握手：1 RTT。
    2. 数据传输：3000B / 1000B = 3个报文段。忽略传输时延，H发出3个段。S收到第3个段，回复ACK。ACK回到H需要 0.5 RTT。此时H确认数据已送达。
    3. 四次挥手：H发FIN（第1次挥手）。S收到FIN，回复ACK（第2次挥手）。S发FIN（第3次挥手）。H收到FIN，回复ACK（第4次挥手）。
    *关键点*：H进入CLOSED状态是在发送完第4次挥手的ACK之后。
    时间轴：
    - T=0: H发SYN
    - T=0.5RTT: S收到SYN，发SYN+ACK
    - T=1.0RTT: H收到SYN+ACK，发ACK（连接建立）。**此时H处于ESTABLISHED**。
    - 数据传输：H发送3个数据段。忽略传输时延，视为T=1.0RTT时发出。
    - T=1.5RTT: S收到第3个数据段，发ACK。
    - T=2.0RTT: H收到ACK。数据确认完毕。
    - 题目说“报文传输结束后H首先请求断开”。通常理解为H在数据发送完成后立即发起关闭。如果H在T=1.0RTT发完数据，它可能不会等ACK就发FIN吗？TCP是全双工，H可以发完数据后立即发FIN。但为了严谨，通常认为“传输结束”指数据被对方确认，或者指发送方发送动作结束。若指发送动作结束，H在T=1.0RTT发完数据，紧接着发FIN。
    - 让我们看选项：30s或60s。这暗示了MSL的影响。
    - 四次挥手时序：
      - H发FIN (T_data_end + 0)
      - S收到FIN，发ACK (T_data_end + 0.5RTT)
      - S发FIN (T_data_end + 0.5RTT, 假设S无延迟)
      - H收到FIN，发ACK (T_data_end + 1.0RTT)
      - H进入TIME_WAIT，等待2MSL。
      - H进入CLOSED = T_data_end + 1.0RTT + 2MSL。
    - 如果T_data_end是数据发送完成时刻（T=1.0RTT），则总时间 = 1.0RTT (握手) + 0 (数据发送) + 1.0RTT (挥手前两个步骤+后两个步骤的ACK到达) + 2MSL?
    - 让我们仔细推导标准答案D (60.04s) 的来源。
    - 60.04s = 2 * 30s + 0.04s。
    - 0.04s = 40ms = 4 RTT。
    - 这意味着除了2MSL，还有4个RTT的开销。
    - 握手：1 RTT。
    - 挥手：通常算1 RTT (FIN->ACK->FIN->ACK，其中FIN和ACK可以合并，或者视为1个RTT完成交互)。
    - 数据：3000B，3个MSS。如果按慢启动，1, 2, 4... 但这里只发3个。
    - 如果答案是4 RTT + 2 MSL：
      - 握手：1 RTT。
      - 数据发送及确认：？
      - 挥手：1 RTT。
      - 剩余2 RTT去哪了？
    - 另一种可能：题目中的“报文传输结束”指的是**最后一个数据段的ACK到达H**？
      - 握手：1 RTT。
      - 数据：H发3个段。S收到第3个段（T=1.5RTT），发ACK。H收到ACK（T=2.0RTT）。此时“传输结束”（从H视角，数据已安全送达）。
      - 挥手开始：H发FIN（T=2.0RTT）。
      - S收到FIN（T=2.5RTT），发ACK（T=2.5RTT）。
      - S发FIN（T=2.5RTT）。
      - H收到FIN（T=3.0RTT），发ACK（T=3.0RTT）。
      - H进入TIME_WAIT。
      - H等待2MSL。
      - 总时间 = 3.0 RTT + 2 MSL = 30ms + 60s = 60.03s。
      - 选项A是30.03s，C是60.03s。
      - 为什么是D (60.04s)？即4 RTT + 2 MSL。
      - 难道数据发送需要更多时间？或者挥手需要更多时间？
      - 如果“报文传输结束”仅指H发完数据（T=1.0RTT），然后H发FIN。
        - H发FIN (T=1.0)。
        - S收FIN (T=1.5)，发ACK (T=1.5)。
        - S发FIN (T=1.5)。
        - H收FIN (T=2.0)，发ACK (T=2.0)。
        - H进入TIME_WAIT。
        - 总时间 = 2.0 RTT + 2 MSL = 20ms + 60s = 60.02s。无此选项。
      - 让我们回顾TCP挥手细节。
      - 第一次挥手：H -> FIN -> S
      - 第二次挥手：S -> ACK -> H
      - 第三次挥手：S -> FIN -> H
      - 第四次挥手：H -> ACK -> S
      - H进入CLOSED是在发送完ACK之后。
      - 如果S的FIN和ACK是分开发送的（标准四次挥手），且S处理有延迟？题目说“至少”，假设无处理延迟。
      - 关键在于**数据阶段的RTT计数**。
      - 3000B数据，MSS=1000B。
      - 如果考虑**慢启动**：
        - 第1个RTT内：发送1个MSS (1000B)。
        - 第2个RTT内：发送2个MSS (2000B)。
        - 总共3个MSS。
        - 时间线：
          - T=0: SYN
          - T=1RTT: 连接建立。H发送第1个MSS。
          - T=1.5RTT: S收到第1个MSS，发ACK。
          - T=2.0RTT: H收到ACK，拥塞窗口变为2。H发送第2、3个MSS。
          - T=2.5RTT: S收到第2、3个MSS，发ACK。
          - T=3.0RTT: H收到ACK。数据全部确认。
          - 此时H发起断开。
          - T=3.0RTT: H发FIN。
          - T=3.5RTT: S收到FIN，发ACK。
          - T=3.5RTT: S发FIN。
          - T=4.0RTT: H收到FIN，发ACK。
          - H进入TIME_WAIT。
          - 等待2MSL。
          - 总时间 = 4.0 RTT + 2 MSL = 40ms + 60s = 60.04s。
      - 这个逻辑完美契合选项D。
      - 因此，K2评分为3，因为需要识别出“慢启动”机制对数据传输时延的影响（1+2=3个MSS，跨越2个RTT的数据发送周期，加上握手的1个RTT，共3个RTT到达数据确认点，再加挥手的1个RTT，共4个RTT）。如果不考虑慢启动，直接发送，时间会不同。题目虽未明说“慢启动”，但“至少”和MSS限制通常暗示考察TCP的流量/拥塞控制基本行为，或者仅仅是分片发送的时序。但在408中，默认初始cwnd=1 MSS是常见考点。

- **K3 = 4**: 评分理由。推演步骤多：1. 握手(1RTT) -> 2. 慢启动数据发送(1个MSS在第一个RTT, 2个MSS在第二个RTT) -> 3. 数据确认(第3个RTT结束) -> 4. 挥手交互(第4个RTT结束) -> 5. TIME_WAIT等待(2MSL)。每一步的状态转换和时间累加都需要清晰逻辑，特别是慢启动阶段的数据发送时机。
- **K4 = 5**: 评分理由。存在多个深层隐含前提和陷阱：
    1. **慢启动机制**：题目未明确提及“慢启动”，但给出了MSS和总数据量，且选项差异在于RTT的数量。若忽略慢启动，直接发送，结果会是3RTT或2RTT，导致选错。这是最大的暗坑。
    2. **“报文传输结束”的定义**：是指发送方发完，还是接收方确认完？结合“H首先请求断开”，通常指H确认数据已安全发送（收到ACK）后才发起FIN，或者H发完数据后立即发FIN。结合答案反推，必须是“收到所有数据ACK后”才发起FIN，或者慢启动导致的发送延迟被计入。
    3. **MSL与TIME_WAIT**：必须知道H进入CLOSED前需等待2MSL，且2MSL是从发送最后一个ACK开始算的。
    4. **单位换算**：ms与s的混合。
- **K5 = 3**: 评分理由。主要涉及TCP传输层内部的状态机流转，未涉及网络层或应用层的复杂交互，但需要在“拥塞控制”和“连接管理”两个子模块间联动（慢启动影响数据发送时间，进而影响挥手开始时间）。
